# 飞书工具状态与交互展示设计文档

## 概述

本设计用于统一 AIPP 在飞书中的工具执行展示方式，使工具调用过程既可读又可交互，并且避免把内部原始文本、长 JSON、附件正文或技能提示词整段转发到飞书。最终效果需要满足“能看懂当前在做什么、能看到关键结果、能在必要时继续交互”，同时覆盖你提出的 MCP 工具加载、Todo 展示、文件预览、子任务派发、命令执行、文件操作和附件格式化场景。

## 功能范围

### 包含范围

- `load_mcp_server`：展示工具集加载结果。
- `load_mcp_tool`：展示工具用途与使用说明摘要。
- `todo_write`：将当前 Todo 状态同步到飞书。
- `preview_file`：按内容类型展示文本、图片、PDF、HTML 或多文件预览结果。
- `spawn_task_conversation`：将结构化字段整理为可读卡片。
- `execute_bash`、`get_bash_output`：展示命令发起、运行结果和失败信息。
- `read_file`、`write_file`、`edit_file`：展示文件路径、操作结果和必要摘要。
- 用户消息中的 `fileattachment`、`skillattachment`、普通 attachment：统一做摘要化展示。
- `ask_user_question` 等需要用户继续决策的场景：保留卡片交互能力。

### 不包含范围

- 不定义底层 API、数据库表和完整 JSON 协议。
- 不把飞书做成桌面端预览组件的完全替代品。
- 不在飞书中默认展示完整文件正文、完整 schema 或完整附件内容。

## 设计目标

- 展示统一：所有工具都遵循一致的状态模型和文案风格。
- 信息克制：默认只发摘要和关键字段，不发原始协议文本。
- 渠道匹配：文本发文本，图片发图片，结构化状态发卡片，用户输入场景发交互卡片。
- 可继续操作：需要用户确认、补充或审批时，优先使用交互卡片。
- 易扩展：新增工具时，只需补充映射规则，不再把逻辑继续堆在中心模块。

## 飞书展示能力与推荐使用方式

飞书适合承担四类展示能力：

| 场景 | 推荐形态 | 适用内容 |
| --- | --- | --- |
| 简短进度与结果 | 文本或 Markdown 卡片 | 工具开始执行、完成提示、轻量摘要 |
| 结构化状态 | 交互卡片 | 子任务、Todo、工具集/工具说明、命令结果、失败说明 |
| 富媒体预览 | 图片消息或带图片区块的卡片 | 图片、截图、图表、单张可视化结果 |
| 用户输入与审批 | 交互卡片 | `ask_user_question`、权限确认、后续动作按钮 |

结合当前系统，建议把飞书外发能力分成三层：

1. **文本层**：继续承接简短提示和兜底输出。
2. **卡片层**：承接大部分结构化工具状态。
3. **媒体层**：补充图片与文件直发能力，满足“文本发文本、图片发图片、文件发文件”。

## 统一状态模型

所有工具在飞书中的展示都使用统一状态语义：

| 状态 | 含义 | 展示要求 |
| --- | --- | --- |
| 已发起 | 工具已被调用，尚未返回结果 | 展示工具名、目标对象、关键参数摘要 |
| 执行中 | 需要持续一段时间，或后续还有输出 | 展示当前动作和最近一条进度摘要 |
| 等待输入 | 需要用户补充信息、审批或选择 | 使用交互卡片，不使用纯文本 |
| 已完成 | 工具已成功完成 | 展示结果摘要、关键产物、下一步上下文 |
| 已失败 | 工具执行失败 | 展示失败原因、失败对象和建议动作 |
| 已展示 | 结果已同步到飞书或外部预览已完成 | 用于 `preview_file`、Todo 同步等“已投递”类场景 |

统一展示原则如下：

- 标题行只说“动作 + 对象 + 状态”，例如“读取文件完成”“已加载 3 个 MCP 工具”。
- 第二层只放关键字段，不展开原始 JSON。
- 超长输出统一截断，并提供“继续查看”的后续动作，而不是一条消息发完。
- 错误信息保留可定位内容，但仍然做长度控制。

## 工具展示设计

### 1. `load_mcp_server`

该工具的价值是让飞书侧知道“当前加载了哪些 MCP 工具集”。推荐使用 **摘要卡片**，而不是只发一句“加载成功”。

卡片应展示：

- 匹配到的工具集数量。
- 每个工具集的名称。
- 每个工具集下的工具数量。
- 每个工具集的简短摘要。

推荐文案：

- 已发起：`正在加载 MCP 工具集：{关键词}`
- 已完成：`已加载 {n} 个 MCP 工具集`
- 已失败：`未找到匹配的 MCP 工具集`

不建议直接把返回 JSON 原样发到飞书。工具集下的工具名可以以列表方式展示，但不展开完整 schema。

### 2. `load_mcp_tool`

该工具的核心不是“加载成功”四个字，而是“把工具使用说明带到当前上下文”。因此推荐使用 **说明型卡片**。

卡片应展示：

- 加载到的工具数量。
- 每个工具的 `server/tool` 名称。
- 工具用途摘要。
- 参数说明摘要，只保留最重要的必填参数和说明。

推荐文案：

- 已发起：`正在加载 MCP 工具说明`
- 已完成：`已加载 {n} 个 MCP 工具说明`
- 已失败：`未找到匹配工具，请换更具体的关键词`

展示原则：

- 默认不展示完整 JSON Schema。
- 默认只展示参数名、用途和必填性。
- 只有在用户明确追问“完整参数定义”时，才追加详细说明。

### 3. `todo_write`

`todo_write` 在飞书中的展示重点是“当前执行面板”，适合使用 **状态卡片**。

卡片应展示：

- 当前 Todo 总数。
- `pending / in_progress / done / blocked` 数量。
- 当前正在执行的 Todo。
- 最近刚完成或刚阻塞的 Todo。

推荐文案：

- 已发起：`正在更新执行 Todo`
- 已完成：`Todo 状态已同步`

如果一次更新只改动单个 Todo，卡片也应明确显示：

- 标题
- 新状态
- 依赖是否已满足
- 必要说明

这样飞书侧能看到执行节奏，而不是只收到“更新成功”。

### 4. `preview_file`

这个工具必须按内容类型走不同展示方式，不能统一降级为一句“预览内容已展示”。

推荐规则如下：

| 文件类型 | 推荐展示方式 | 展示内容 |
| --- | --- | --- |
| `text` / `markdown` | Markdown 卡片或文本消息 | 标题、语言、前几屏内容、必要说明 |
| `image` | 图片消息或带图片区块卡片 | 图片本身、标题、说明 |
| `pdf` | 文件消息或摘要卡片 | 文件名、说明、下载入口 |
| `html` | 摘要卡片 | 标题、说明、访问入口，不直接发原始 HTML |
| 多文件 | 汇总卡片 | 文件列表、类型、切换顺序；必要时拆多条消息 |

业务规则：

- 文本文件默认截断展示，不把全文直接发到飞书。
- 图片优先直接展示图片，而不是把图片路径当文本发出。
- PDF 和二进制文件优先作为文件发送；如果当前链路暂不支持文件直发，则退化为摘要卡片。
- 多文件预览不模拟桌面端 tab，而是发一张汇总卡片，必要时再分多条详细消息。

### 5. `spawn_task_conversation`

这个工具天然适合卡片化，因为参数本身是结构化的。推荐使用 **子任务卡片**。

卡片应展示：

- 子任务标题。
- 执行助手。
- 任务目标摘要。
- 当前状态：已派发、执行中、完成、失败。
- 任务结果摘要。

推荐文案：

- 已发起：`已派发子任务`
- 已完成：`子任务已完成`
- 已失败：`子任务执行失败`

展示原则：

- 不发原始 JSON。
- `goal` 只展示摘要，不直接透传完整长提示词。
- 如有任务编号或会话编号，可作为次级字段展示。

### 6. `execute_bash` / `get_bash_output`

命令执行信息容易过长，推荐使用 **命令状态卡片**。

卡片应展示：

- 命令描述；如果没有描述，则展示截断后的命令行。
- 当前状态：已发起、已完成、已失败、后台输出已更新。
- 最近一段 stdout/stderr 摘要。
- 必要时展示退出状态。

推荐文案：

- 已发起：`正在执行命令：{description 或 command}`
- 已完成：`命令执行完成`
- 已失败：`命令执行失败`
- 输出更新：`后台命令输出已更新`

业务规则：

- 默认只发最近一段输出，避免刷屏。
- 连续输出应聚合，不要每一行都发一条消息。
- 如果命令是后台任务，后续输出更新应追加到同一任务语义下，而不是伪装成全新任务。

### 7. `read_file` / `write_file` / `edit_file`

这类工具的重点是“操作了哪个文件，结果如何”，而不是把文件内容原样塞给飞书。

推荐展示如下：

| 工具 | 已发起 | 已完成 | 已失败 |
| --- | --- | --- | --- |
| `read_file` | `正在读取文件 {path}` | `文件读取完成：{path}` | `文件读取失败：{path}` |
| `write_file` | `正在写入文件 {path}` | `文件写入完成：{path}` | `文件写入失败：{path}` |
| `edit_file` | `正在编辑文件 {path}` | `文件编辑完成：{path}` | `文件编辑失败：{path}` |

增强展示建议：

- `read_file` 成功时，追加文件大小、行数或摘要首屏。
- `write_file` 成功时，追加写入对象和字节规模。
- `edit_file` 成功时，追加“修改摘要”，例如改动行数或变更主题。

只有在显式调用 `preview_file` 时，才把正文内容进一步展示到飞书。

## 用户消息格式化规则

用户消息不能把原始标签、附件正文、技能提示词、内联大文本直接转发到飞书。必须先做摘要化。

### 1. `fileattachment`

推荐转成用户可读摘要：

- 图片：`[图片附件] {文件名}`
- 文档：`[文件附件] {文件名}`
- 未知类型：`[附件] {显示名}`

规则：

- 不转发标签体内容。
- 不转发 base64 正文。
- 保留文件名、类型、可选说明。

### 2. `skillattachment`

推荐转成技能摘要，而不是把技能正文和 invocation 整段发出去。

建议格式：

- `[技能附件] {skill_name}`
- `标识符：{identifier}`

不展示内容：

- `invocation`
- 技能正文
- 内部提示词

这与当前前端“只显示用户可见技能元信息、不泄露正文”的方向保持一致。

### 3. 普通 attachment / 用户附带上下文

普通附件和上下文统一用“摘要块”呈现：

- 标题
- 类型
- 来源路径或标识
- 可选一句说明

如果一条用户消息内包含多个附件，飞书中应显示为：

- 用户正文
- 附件摘要列表

而不是把每个附件的原始内容穿插进正文。

## 推荐架构方案

推荐在现有外部渠道渲染链路之上增加一个更高层的“展示负载”抽象，而不是继续只返回字符串。

### 整体架构

1. **Projection 层**：把内部消息、工具调用和工具结果转换成统一的结构化事件。
2. **Policy 层**：根据工具类型、状态和内容类型，决定发送文本、卡片、图片还是文件。
3. **Delivery 层**：负责真正调用飞书发送能力。

### 推荐输出模型

展示层应至少支持以下输出类型：

- `text`
- `interactive_card`
- `image`
- `file`

这样才能满足“文本发文本、图片发图片、文件发文件、结构化字段发卡片”的目标。

### 与现有实现的关系

当前系统已经具备：

- 外部渠道消息渲染入口。
- 工具调用/结果的基础可读化。
- 飞书文本和交互卡片发送能力。
- `ask_user_question` 交互卡片能力。

因此推荐方案不是重做一套，而是把当前“字符串渲染”提升为“结构化展示决策”，并补齐图片、文件两类外发能力。

## 业务规则

- 同一条工具事件只能选择一种主展示形态，避免一会儿发文本、一会儿又发重复卡片。
- 能摘要就摘要，不能摘要再降级文本，不能直接透传原始协议文本。
- 文件正文、附件正文、技能正文默认不外发。
- 长输出要截断并可继续追发，不能一条消息承载全部内容。
- 需要用户决策的内容必须用交互卡片优先承载。
- 多文件和多工具结果优先做聚合卡片，避免飞书刷屏。

## 非功能需求

- **可读性**：飞书中的每一条消息都应让用户在几秒内看懂“在做什么、现在结果如何”。
- **安全性**：不泄露技能正文、原始附件正文、长提示词和本地敏感上下文。
- **一致性**：同类工具使用一致的标题、状态和字段布局。
- **扩展性**：新增工具时可按映射规则补充，不需要继续堆大量分支判断。

## 验收标准

- [ ] `load_mcp_server` 能在飞书中展示工具集名称、数量和摘要，而不是原始 JSON。
- [ ] `load_mcp_tool` 能展示工具用途与关键参数摘要，而不是只显示“加载成功”。
- [ ] `todo_write` 能把 Todo 总览和当前执行状态展示到飞书。
- [ ] `preview_file` 能根据内容类型分别走文本、图片、文件或摘要卡片展示。
- [ ] `spawn_task_conversation` 能以结构化卡片展示标题、执行者、目标和结果。
- [ ] `execute_bash` / `get_bash_output` 能按任务语义展示命令状态与输出摘要。
- [ ] `read_file` / `write_file` / `edit_file` 能展示路径、结果和必要摘要，不默认外发全文。
- [ ] `fileattachment`、`skillattachment`、普通附件在用户消息中都经过摘要化处理，不泄露正文。
- [ ] 需要用户输入的场景优先使用交互卡片。
