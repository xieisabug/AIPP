# Benchmark 题目图片附件设计文档

## 概述

Benchmark 支持在每个题目下附加图片附件，用于构建视觉问答、截图理解、图表分析等多模态题目集。该能力覆盖题目录入、导入、编辑、运行和评分全流程，并保持与现有文本 benchmark 一致的使用体验。

## 功能范围

### 包含范围

- 每个题目支持维护独立的附件列表，当前附件类型限定为图片。
- 题目支持文本题干、标准答案与图片附件的组合录入。
- 题目支持图片附件的新增、删除、排序、预览与替换。
- 题目支持通过导入方式批量建立图片附件题目集。
- Benchmark 运行时，Runner 能收到题干与图片附件组成的完整输入。
- Benchmark 评分时，Judge 能收到题干、图片附件、标准答案与 Runner 输出组成的完整上下文。
- 运行记录保留题目级附件快照信息，保证结果可追溯。

### 不包含范围

- 视频、音频、PDF、Office 文档作为题目附件的正式支持。
- 通用数据集市场、远程同步、共享题库。
- 复杂标注能力，例如框选、区域问答、多轮视觉对话。
- 面向所有插件开放的完整多媒体资产管理中心。

## 用户场景

### 目标用户

- 使用 AIPP 进行模型评测的产品、研发、算法和测试人员。
- 需要构建视觉理解题集的内部评测用户。
- 希望比较不同模型在图像理解任务上表现的使用者。

### 使用场景

场景 1：为每道题附加截图，评测模型对界面元素、报错信息和布局状态的理解能力。  
场景 2：为每道题附加图表或信息图，评测模型对图形内容的阅读与推理能力。  
场景 3：通过批量导入方式快速建立图片问答题集，并持续复用同一套评测数据。

## 功能详情

### 题目模型

每个 Benchmark 题目由三类信息组成：

- 题干文本
- 标准答案
- 附件列表

附件列表采用可扩展结构设计，当前仅启用图片类型。这样可以在不重做题目模型的前提下，后续平滑扩展到视频等其他模态。

### 题目录入与编辑

题目编辑区需要支持题干、标准答案和附件的统一维护。用户可以在单题维度完成以下操作：

- 选择本地图片作为题目附件
- 查看缩略图和基础信息
- 调整图片顺序
- 删除错误图片
- 替换已有图片

附件编辑能力应与题目文本编辑保持同一上下文，避免用户在题目管理与文件管理之间来回切换。

### 批量导入

批量导入应覆盖“文本字段 + 图片引用”的导入需求。导入能力需要支持以下形式：

- 表格中直接描述图片路径或图片 URL
- 以导入根目录为基准解析相对路径
- 对导入失败的题目给出逐条错误反馈

导入的目标是快速建立题目集，而不是要求用户在导入前手工逐题上传图片。

### 运行流程

执行 Benchmark 时，系统以“题干 + 图片附件”作为题目的完整输入交给 Runner。这样视觉模型能直接基于原始图像作答，而不是依赖转写文本。

评分阶段，Judge 接收同一题目的原始输入、标准答案和 Runner 输出，形成完整判分上下文。这样可以避免题目依赖图片内容而 Judge 却只能看到文本的失真问题。

### 结果记录

运行结果需要保留题目级附件引用，以便用户回看每一道题时，能够同时看到：

- 原始题干
- 原始图片附件
- 标准答案
- Runner 输出
- Judge 评分结论

这类记录不仅用于查看结果，也用于后续复盘、复跑和排行榜解释。

## 业务规则

- 当前阶段仅支持图片附件，题目中出现其他文件类型时不进入正式运行流程。
- 题目允许无附件，文本题目继续按现有方式运行。
- 含图片附件的题目只能由支持图像输入的 Runner 执行。
- 含图片附件的题目只能由具备相应判分能力的 Judge 执行。
- 题目一旦进入运行，使用的是当次运行快照，不受后续题目编辑影响。
- 图片附件进入题目集后应转化为宿主可管理的内部资源，避免运行时依赖外部文件路径稳定性。
- 导入过程中图片缺失、不可读取或格式不支持时，该题目应被标记为校验失败，而不是静默忽略。

## 架构设计

### 整体架构

该能力建议采用四层结构：

| 层级 | 职责 |
| --- | --- |
| Benchmark 插件界面层 | 负责题目编辑、附件选择、导入预览、运行配置和结果展示 |
| 插件多模态调用层 | 负责把题目文本与附件组装为插件可消费的标准输入 |
| 宿主附件与多模态桥接层 | 负责附件入库、能力校验、模型调用与消息内容组装 |
| Benchmark 持久化与运行层 | 负责题目集、运行快照、结果记录与排行榜聚合 |

这四层需要明确边界：插件负责业务界面，宿主负责附件资源管理和多模态消息构造，运行层负责评测生命周期。

### 技术选型

- 附件资源管理复用宿主现有附件存储能力，避免 benchmark 自建文件系统。
- 多模态消息构造复用宿主现有对话链路中的图片处理能力，保持模型输入格式一致。
- Benchmark 插件不应长期依赖“任意命令直调”作为正式接口，而应收敛为插件 SDK 的官方多模态能力。
- 题目模型采用“文本字段 + 附件列表”的统一结构，兼容纯文本题目与未来视频题目。

### 扩展性考虑

- 附件结构预留类型字段，为后续视频扩展保留入口。
- Runner 与 Judge 的能力校验从一开始就按“模型输入能力”抽象，不做图片特例硬编码。
- 导入能力按“字段映射 + 附件解析”抽象，可继续扩展到更多来源。
- 结果展示按“题目输入快照”抽象，后续扩展视频时无需重做结果页信息架构。

## 技术方案

### 方案对比

| 方案 | 描述 | 优点 | 局限 |
| --- | --- | --- | --- |
| 方案 A | Benchmark 插件直接调用宿主现有附件命令和对话命令 | 改动小，复用快 | 插件依赖内部命令，边界不稳定 |
| 方案 B | 扩展插件 SDK，提供正式的多模态题目调用能力 | 能力清晰，可复用，可维护 | 需要同步扩展插件运行时与桥接层 |

### 推荐方案

推荐采用“宿主附件链路复用 + 插件 SDK 正式扩展”的方案。

该方案以宿主现有图片输入能力为基础，不重复建设附件处理逻辑；同时把多模态题目能力沉淀为插件体系的正式接口，避免 Benchmark 成为特殊插件。这样既能满足本期图片题目需求，也能为未来视频支持建立稳定边界。

### 技术难点

- 插件层需要拿到清晰、稳定的图片附件能力，而不是只具备纯文本调用能力。
- 运行前需要判断 Runner 和 Judge 是否具备图像输入能力，避免错误执行。
- 批量导入时需要同时处理文本字段和图片资源解析，保证错误反馈清晰。
- 结果记录必须保存题目快照，避免题目被编辑后导致历史结果不可解释。

## 非功能需求

- **性能**：题目编辑与附件预览应保持流畅，批量导入应具备明确的进度和错误反馈。
- **可靠性**：图片入库后不依赖原始本地路径；运行时不存在因外部文件变动导致的不可复现问题。
- **可用性**：纯文本题目与图片题目共存，用户无需切换不同的题目管理模式。
- **一致性**：插件内的图片输入体验、模型调用体验与主聊天区保持同一产品语义。
- **可扩展性**：后续增加视频支持时，题目结构、运行结构和结果结构无需推倒重来。

## 验收标准

- [ ] 用户可以在单个 Benchmark 题目下新增、删除、预览和排序图片附件。
- [ ] 纯文本题目与图片题目可以在同一题目集中共存。
- [ ] 图片题目运行时，Runner 实际接收到题干与图片组成的多模态输入。
- [ ] 图片题目评分时，Judge 可以基于题干、图片、标准答案和 Runner 输出进行判分。
- [ ] 含图片附件的题目在不支持图像输入的模型上会被明确阻止执行。
- [ ] 批量导入支持建立带图片附件的题目，并对失败项提供清晰反馈。
- [ ] 运行记录中可以回看题目原始图片附件及对应评分结果。
- [ ] 文本 benchmark 的现有使用方式不受影响。
