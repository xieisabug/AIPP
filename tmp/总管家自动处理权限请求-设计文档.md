# 总管家自动处理权限请求

## 概述

总管家需要从“权限请求的展示入口”升级为“权限请求的实际处理者”。系统在任务执行过程中遇到操作权限或 ACP 工具权限时，应优先由总管家运行时自动判断、自动决策、自动放行或拒绝，只有在高风险、低置信度或超出策略边界时才回退给人工处理。

该能力的目标不是减少弹窗本身，而是把权限处理从前端人工交互链路下沉到总管家后端运行时，让任务可以在安全边界内持续推进，而不是停在“待审批”状态等待人点击。

## 功能范围

### 包含范围

- 总管家任务中的操作权限自动处理
- 总管家任务中的 ACP 工具权限自动处理
- 自动决策失败时的人工兜底
- 人工审批在桌面端与飞书端的双通道处理
- 飞书不可用或交互卡片不可用时的关键词回复降级
- 权限决策结果的可追溯记录
- 总管家任务列表与详情中的权限处理状态反馈

### 不包含范围

- 普通聊天窗口的通用权限系统重写
- 非总管家场景下的全面自动授权
- 首版就提供复杂的可视化策略编辑器

## 当前状态

### 当前权限链路

- 操作权限在本地白名单、会话信任路径、助手工作区都无法命中时，会进入 `request_permission`，随后发出 `operation-permission-request` 事件并阻塞等待结果。
- ACP 权限在需要确认时，会发出 `acp-permission-request` 事件并阻塞等待结果。
- 总管家窗口会订阅这些事件，并在任务台显示“待审批”状态，但真正的审批结果仍由前端调用 `confirm_operation_permission` 或 `confirm_acp_permission` 提交。
- 因此，当前总管家只是权限请求的聚合窗口，不是权限请求的处理主体。

### 当前飞书能力

- `ask_user_question` 已经具备飞书投递能力：可以把问题投递成飞书交互卡片，并通过 `card.action.trigger` 回调把结果 resolve 回运行时。
- 飞书文本消息入口也已经存在，所有 `im.message.receive_v1` 文本消息都会进入总管家飞书处理链路。
- 但操作权限与 ACP 权限当前没有对应的飞书审批桥接能力：既没有专门的飞书权限卡片，也没有把飞书回调结果路由到 `confirm_operation_permission` / `confirm_acp_permission` 的实现。
- 这意味着“飞书能问问题”已经有基础，但“飞书能审批权限”目前还没有直接打通。

### 核心问题

1. 任务执行会被人工审批链路卡住，无法形成真正的自动闭环。
2. 总管家虽然能看到任务状态，却不能代表系统做决定。
3. 当前“待审批”只是一种 UI 呈现，不是总管家运行时的自主能力。
4. 权限处理逻辑分散在前端交互和后端等待之间，不利于后续扩展成策略化、可审计的自动审批。

## 用户场景

### 目标用户

- 使用总管家派发复杂任务、希望任务自行推进的用户
- 需要在受控目录或受控工具范围内长期自动执行任务的用户

### 使用场景

场景 1：总管家派发代码整理任务，执行助手需要读取和编辑工作区文件，总管家根据既有策略自动放行，无需人工点击。

场景 2：执行助手申请访问工作区外目录或高风险 ACP 操作，总管家判断超出策略范围，自动转为人工审批。

场景 3：夜间或无人值守场景下，总管家基于安全策略自动处理大部分低风险请求，仅在必要时留下待人工处理项。

## 功能详情

### 功能点一：引入总管家权限决策运行时

在后端新增统一的权限决策层，作为操作权限和 ACP 权限的共同入口。权限请求进入该层后，不再默认直接发往前端，而是先由总管家运行时尝试自动处理。

这一层的职责包括：

- 标准化权限请求上下文
- 执行规则匹配与风险判定
- 决定自动允许、自动拒绝或转人工审批
- 记录决策来源、理由和结果

### 功能点二：采用“规则优先，模型补充，人工兜底”的三层决策机制

首选确定性规则，不把所有权限问题都交给模型判断。

推荐的决策顺序如下：

1. **已有系统信任命中**：沿用当前已有的白名单、会话信任路径、助手工作区判断，命中后直接通过。
2. **总管家规则引擎命中**：对已知低风险行为直接自动处理，例如任务工作目录内的读取、同一工作区内的有限编辑、明确标记为低风险的 ACP 一次性许可。
3. **总管家智能裁决**：规则无法覆盖时，由总管家权限裁决器根据任务目标、助手身份、权限内容、历史决策和风险级别生成结构化决策。
4. **人工审批回退**：对于高风险、低置信度、跨边界或策略禁止自动处理的请求，继续沿用现有前端审批路径。

### 功能点三：将总管家自动处理限定在任务级安全边界内

总管家不能获得“无限授权”。自动处理必须以任务级策略为边界，不能绕过全局安全约束。

推荐引入任务级权限策略，定义以下内容：

- 可自动处理的权限类型
- 可访问的目录边界
- 可接受的授权范围
- 允许自动处理的 ACP 选项范围
- 必须升级为人工审批的高风险条件

该策略应与总管家任务定义绑定，而不是散落在前端页面状态中。

### 功能点四：保留人工审批作为降级路径

自动处理不是替代人工审批，而是减少人工介入频次。对于以下情况，系统应明确转为人工审批：

- 写入工作区外路径
- 申请加入全局白名单
- ACP 中的永久授权选项
- 删除、覆盖、批量修改等高影响并且无法判断是否真的合规的操作
- 模型无法给出高置信度结论

### 功能点五：增加权限处理审计与可见性

用户需要知道“是谁决定的、为什么决定、决定了什么”。因此应保留完整审计轨迹，并在总管家界面中展示简明结果。

推荐呈现内容包括：

- 权限请求类型
- 请求目标
- 决策结果
- 决策来源：规则 / 总管家自动裁决 / 人工审批
- 决策理由摘要
- 发生时间

## 业务规则

- 总管家自动处理仅对总管家任务会话生效，不默认扩展到所有会话。
- 当前已有的安全校验顺序保留，不能因为自动化而跳过本地白名单、会话信任、助手工作区等已有判断。
- 自动处理优先产出一次性或会话级许可，永久性授权必须更谨慎。
- 对高风险操作，默认保守，优先转人工审批。
- 任何自动决策都必须可审计、可追踪、可回放。

## 架构设计

### 整体架构

推荐新增一个后端模块，作为总管家的权限编排器，统一接入两类请求：

- 操作权限请求
- ACP 工具权限请求

该模块位于权限请求发出前、前端事件发出前，形成如下链路：

`权限请求产生 -> 总管家权限编排器 -> 自动决策 / 人工回退 -> 结果写回现有等待通道`

这样可以尽量复用当前的 `oneshot` 等待机制，不必重做整个任务阻塞与恢复流程。

### 总管家与子任务的权限交互方式

这部分是本方案的核心。总管家与子任务之间不应该通过“主会话里看见一个待审批提示，再让人手动点按钮”的方式耦合，而应该通过后端控制面交互。

推荐采用下面的职责划分：

- **子任务会话**：权限请求的发起方，也是最终继续执行或被拒绝的一方
- **总管家权限编排器**：统一接住子任务发来的权限请求，负责自动决策或发起人工审批
- **总管家权限裁决器**：编排器内部的决策执行面，可以是规则引擎，也可以是隐藏的智能裁决器
- **总管家主界面**：状态展示与人工介入入口，不承担权限逻辑本身
- **飞书渠道**：人工审批的外部入口，不直接持有权限状态，只提交决策

具体时序建议如下：

1. 子任务在自己的任务会话中触发操作权限或 ACP 权限请求。
2. 请求先写入对应的待处理状态池，并保留 `request_id`、`task_conversation_id`、`butler_conversation_id`、请求详情、可选决策范围等元信息。
3. 总管家权限编排器读取任务定义，拿到父总管家主会话、执行助手、任务目标、权限模板来源等上下文。
4. 编排器先执行确定性规则；命中则直接给出决策并回填到原始等待通道。
5. 规则未命中时，编排器调用总管家权限裁决器；这里的“总管家”应是隐藏的后端运行时，而不是用户可见的主会话。
6. 若自动裁决成功，编排器直接 resolve 原请求，并给任务台推送“已自动处理”的结果。
7. 若必须人工介入，编排器创建一个 `PermissionReviewTicket`，再同时向桌面端和飞书端发出审批请求。
8. 任一渠道先提交成功，均通过统一的 `confirm_*` 路径完成真正 resolve；其他渠道收到 resolved 事件后自动关闭或标记已处理。

这套设计里，真正被阻塞的是子任务，不是总管家主会话。总管家主界面只负责观察和介入，避免主会话被卡在等待态。

### 状态归属与并发处理

为了让桌面端和飞书端都能处理同一个权限请求，又不出现“双重审批”问题，建议遵循以下规则：

- 待处理权限的唯一真相仍然保存在后端状态里，不放在前端或飞书卡片里。
- `confirm_operation_permission` 和 `confirm_acp_permission` 继续作为统一提交入口。
- 桌面端、总管家窗口、飞书卡片、飞书关键词回复都只是在调用同一个确认入口。
- 第一个成功提交的渠道生效；后续重复提交会得到“该请求已处理”的结果。
- 提交成功后，通过现有 resolved event 广播，让 Butler 窗口和其他前端监听器移除待处理项。

这意味着我们不需要分别维护“桌面审批状态”和“飞书审批状态”，只需要维护一个统一的后端待处理状态。

### 推荐模块划分

- **Permission Context Builder**：把操作权限和 ACP 权限整理成统一上下文
- **Rule Engine**：执行确定性规则匹配
- **Butler Adjudicator**：负责智能裁决，输出结构化决策
- **Audit Logger**：记录请求、决策、来源和理由
- **Fallback Bridge**：在无法自动处理时走现有前端审批事件

另外建议补一个模块：

- **Permission Review Registry**：统一保存待人工处理请求的事件快照，供 Butler UI、飞书卡片、关键词回复解析复用

### 技术选型

#### 方案一：纯规则引擎

优点：

- 安全边界清晰
- 行为稳定，可预测
- 开发成本较低

不足：

- 覆盖面有限
- 复杂上下文下缺少弹性

#### 方案二：纯模型裁决

优点：

- 灵活度高
- 能结合任务语义做判断

不足：

- 风险较高
- 行为一致性较弱
- 不适合作为第一层决策

#### 推荐方案：规则引擎 + 智能裁决 + 人工回退

这是最适合当前系统的方案。规则引擎负责大部分低风险、可确定场景；智能裁决只处理规则无法覆盖但仍可自动化的中间地带；人工审批保留为最终兜底。

## 技术方案

### 方案落点

#### 操作权限

在操作权限请求进入前端事件发送之前，先调用总管家权限编排器。如果编排器给出自动决策，则直接解析为现有 `PermissionDecision` 并继续后续流程；如果编排器返回“转人工”，再走现有 `operation-permission-request` 事件。

#### ACP 权限

在 ACP 权限请求进入前端事件发送之前，同样先进入总管家权限编排器。若自动裁决成功，则直接回填现有 ACP 权限响应；否则发出 `acp-permission-request` 事件并等待人工处理。

### 待处理权限状态的具体改造

当前操作权限和 ACP 权限的待处理状态只够支撑“等一个结果”，不够支撑“多渠道人工审批”。要做飞书审批，必须把事件快照也保存在后端。

建议改造方向：

- **OperationState**：除了 `sender` 和 `conversation_id`，还要保存操作类型、路径、任务归属、可选决策范围、创建时间
- **AcpPermissionState**：除了 `sender` 和 `conversation_id`，还要保存标题、参数、options、任务归属、创建时间
- 引入统一的 `PermissionReviewTicket` 视图对象，供桌面端和飞书端共同消费

建议 ticket 至少包含：

- `request_id`
- `request_kind`：`operation` / `acp`
- `task_conversation_id`
- `butler_conversation_id`
- `executor_assistant_id`
- `title`
- `summary`
- `risk_level`
- `available_actions`
- `created_at`
- `delivery_channels`

这样飞书侧就不需要直接依赖底层状态结构，而是消费标准化后的审批单。

### 决策输入

总管家权限编排器应至少拿到以下上下文：

- 任务会话 ID 与所属总管家主会话
- 执行助手信息
- 任务标题与目标
- 权限请求类型与内容
- 目标路径或 ACP 参数
- 当前已信任目录与工作区信息
- 最近的权限决策历史

### 决策输出

统一输出三类结果：

- 自动允许
- 自动拒绝
- 转人工审批

输出中还应包含：

- 决策来源
- 风险级别
- 理由摘要
- 建议的授权范围

### 智能裁决形态

不建议直接把可见的总管家主会话当作权限审批执行面。更稳妥的方式是引入一个隐藏的“总管家权限裁决器”，由后端内部调用，避免：

- 干扰用户正在进行的总管家主会话
- 造成主会话上下文污染
- 引入对前端可见会话状态的额外耦合
- 在权限等待期间形成新的会话阻塞或递归依赖

从用户视角看，这仍然是“总管家在自动处理”，只是执行面应放在后端内部运行时，而不是放在可见聊天界面里。

### 人工审批渠道设计

人工审批要做成多渠道并行，而不是单点依赖 Butler 桌面窗口。

#### 桌面端

桌面端继续保留现有权限弹窗与 Butler 任务台展示，这是默认的本地审批入口。

#### 飞书端能力评估

基于现有代码，飞书这块可以分成“已有基础”和“尚未打通”两部分：

- **已有基础**
  - 可以根据会话找到最近的飞书发送目标
  - 可以发送飞书交互卡片
  - 可以接收 `card.action.trigger` 回调
  - 可以把飞书卡片提交结果 resolve 回运行时，但当前仅用于 `ask_user_question`
  - 可以接收普通文本消息，并在后端统一处理

- **当前缺口**
  - 没有 `operation permission -> 飞书卡片` 的投递函数
  - 没有 `acp permission -> 飞书卡片` 的投递函数
  - 卡片回调里没有把权限审批动作分发到 `confirm_operation_permission` / `confirm_acp_permission`
  - 文本消息入口里没有“待审批关键词回复”的拦截解析逻辑

结论：飞书人工审批**不是没有能力基础**，而是**缺最后一段权限桥接**。

#### 首选实现：原生飞书权限审批卡片

推荐为权限审批新增专门的飞书卡片，而不是让飞书看到一个模糊的通知文本。

卡片内容建议包含：

- 任务标题
- 执行助手
- 权限类型
- 操作路径或 ACP 参数摘要
- 风险等级
- 可选动作按钮

操作权限的卡片动作建议为：

- 允许一次
- 本任务信任
- 添加到助手工作区
- 拒绝

其中“加入全局白名单”属于高风险动作，首版不建议放到飞书卡片里直接开放。

ACP 权限则直接映射其原生 options。

实现方式建议：

1. 复用现有的飞书目标发现和卡片发送能力。
2. 为权限请求新增 `build_operation_permission_card` / `build_acp_permission_card`。
3. 在卡片 `action.value` 中写入 `request_kind`、`request_id`、`decision` 或 `option_id`。
4. 扩展 `handle_card_action_trigger`，根据 `request_kind` 分发到 `confirm_operation_permission` 或 `confirm_acp_permission`。
5. 审批成功后回写统一 resolved event，让桌面端自动消失。

#### 低成本 MVP：先复用 ask_user_question 的飞书卡片链路

如果希望更快落地，而不想第一阶段就做原生权限卡片，也可以先做一个中间方案：

- 当权限请求需要人工介入且当前任务已绑定飞书链路时，将其转成一个结构化 `ask_user_question`
- 飞书侧继续走已经成熟的 `ask_user_question -> 交互卡片 -> card.action.trigger -> resolve` 链路
- 后端把问题答案再转换回权限决策

这个方案的优点是复用现有能力多，改动小；缺点是语义上仍然是“用提问模拟审批”，产品形态不如原生权限卡片直接。

因此建议把它作为第一阶段可交付的 Feishu MVP，而把原生权限卡片作为第二阶段增强。

#### 最终降级：关键词回复审批

如果飞书交互卡片不可用、回调不稳定，或者用户明确希望通过文字回复完成审批，则可以进一步降级成关键词回复。

推荐格式如下：

- 操作权限：
  - `批准一次 P123`
  - `本任务批准 P123`
  - `助手批准 P123`
  - `拒绝 P123`
- ACP 权限：
  - `批准 1 P456`
  - `批准 2 P456`
  - `取消 P456`

其中 `P123` / `P456` 是展示给用户的短审批号，对应真实 `request_id`。

实现方式建议：

1. 当人工审批落到飞书文本模式时，系统先发送一条审批说明消息，包含短审批号、候选命令、超简要摘要。
2. 在 `im.message.receive_v1` 的文本消息处理入口增加一个 `try_handle_pending_permission_reply`。
3. 该函数先尝试把文本解析成权限命令；匹配成功则直接调用统一 `confirm_*` 提交入口。
4. 若不匹配，则按原逻辑把文本继续交给总管家主会话处理。

这样不会破坏现有飞书聊天能力，只是在进入总管家主会话之前多了一层待审批解析。

### 关键词回复的安全约束

关键词审批虽然方便，但必须加约束，否则误判风险会很高。

建议至少做以下限制：

- 只处理与机器人最近发出的权限审批消息相关联的回复
- 必须带短审批号，避免一句“批准”误命中
- 仅允许来自当前飞书链路用户或白名单用户的回复生效
- 群聊场景下要求 @机器人 或回复该审批消息
- 同一个审批号只允许成功 resolve 一次

如果这些约束无法保证，则不应启用关键词审批。

## 分阶段实施

### 第一阶段：后端自动审批骨架

- 新增总管家权限编排器
- 打通操作权限和 ACP 权限的统一入口
- 支持规则引擎自动允许 / 自动拒绝 / 转人工
- 保留现有前端审批链路不变作为兜底
- 为待人工处理请求补齐统一 `PermissionReviewTicket`
- 飞书侧先复用 `ask_user_question` 链路做权限审批 MVP

这一阶段就能把“总管家不是处理者，只是展示者”的问题改掉。

### 第二阶段：智能裁决能力

- 为规则未命中的请求增加总管家智能裁决
- 输出结构化决策与理由
- 增加置信度阈值，低置信度自动转人工
- 补齐原生飞书权限卡片与卡片回调分发
- 增加桌面端 / 飞书端并行审批的一致性处理

### 第三阶段：策略与可视化

- 在总管家任务定义中支持权限策略配置
- 在任务详情中展示权限决策历史
- 支持按助手或任务模板沉淀可复用策略
- 增加飞书关键词回复降级与审批审计明细展示

## 非功能需求

- **安全**：默认保守，自动处理不能扩大现有权限边界
- **稳定性**：自动决策失败时必须可靠回退到人工审批，不能让任务卡死
- **可审计性**：每个自动决策都要有来源、理由和时间
- **可扩展性**：后续可以扩展到更多权限类型，但首版不应一次性做太宽
- **可观测性**：需要日志、状态标记和任务详情中的结果反馈

## 风险与应对

### 风险一：自动放行过宽

应对方式：首版只允许低风险规则自动通过，高风险默认转人工，不提供默认永久授权。

### 风险二：模型裁决不稳定

应对方式：模型只做第二层补充，不能替代规则引擎；低置信度直接转人工。

### 风险三：权限请求导致总管家内部递归阻塞

应对方式：使用独立的后端权限裁决器，不复用用户可见主会话作为审批执行面。

### 风险四：用户无法理解任务为何继续或被拦截

应对方式：在任务详情中展示简洁但明确的决策摘要，并保留审计记录。

### 风险五：桌面端和飞书端重复审批或互相打架

应对方式：所有渠道统一走同一个 `request_id` 的确认入口，后端 first-wins，成功后广播 resolved event 清理其他渠道展示。

### 风险六：关键词回复误判为审批指令

应对方式：强制要求短审批号、回复链路校验、发送人校验；解析失败则继续按普通飞书消息处理。

## 验收标准

- [ ] 总管家任务中的权限请求会先进入总管家后端权限编排器，而不是直接弹前端人工审批
- [ ] 低风险、命中策略的请求可以自动完成，不需要人工点击
- [ ] 高风险或低置信度请求可以稳定回退到现有人工审批流程
- [ ] 自动决策后，任务能够继续执行，不会停留在无结果的等待态
- [ ] 用户可以在总管家界面中看见该请求是自动处理还是人工处理
- [ ] 系统可以追踪每次权限决策的来源和理由
- [ ] 人工审批时，如果该任务已绑定飞书链路，用户可以在飞书侧完成审批
- [ ] 桌面端和飞书端审批同一请求时，系统只接受第一份有效决策，其他渠道自动收敛
- [ ] 在飞书交互卡片不可用时，系统可以退化为关键词回复审批，且不会误伤普通聊天消息

## 推荐实施顺序

优先把决策权下沉到后端，再考虑策略编辑和界面美化。也就是说，先解决“总管家是不是处理者”的问题，再解决“总管家如何配置得更灵活”的问题。

首个可交付版本建议只覆盖最常见、最容易界定边界的权限类型：工作区内读取、有限编辑、低风险 ACP 一次性授权。这样可以尽快形成自动闭环，同时把安全风险控制在可接受范围内。
