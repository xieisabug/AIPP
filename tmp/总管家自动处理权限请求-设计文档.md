# 总管家自动处理权限请求

## 概述

总管家需要从“权限请求的展示入口”升级为“权限请求的实际处理者”。当子任务在执行过程中遇到操作权限、ACP 权限或其他需要确认的阻塞时，系统应优先由总管家主动查看子任务会话、理解当前上下文、执行确认或补充指令，只有在超出安全边界或无法可靠判断时才转为人工处理。

该能力的目标不是单纯减少弹窗，而是让总管家真正接管子任务的推进过程，避免任务停在“待审批”状态等待人手点击。

## 功能范围

### 包含范围

- 总管家任务中的操作权限处理
- 总管家任务中的 ACP 工具权限处理
- 总管家对子任务会话的主动查看与操作
- 总管家接到阻塞提醒后的最小上下文判断
- 桌面端与飞书端的人工兜底审批
- 飞书交互卡片不可用时的关键词审批降级
- 权限请求、处理结果与处理来源的统一追踪

### 不包含范围

- 普通聊天窗口的通用权限系统重写
- 非总管家场景下的全面自动授权
- 首版即提供复杂的权限策略可视化编辑器
- 首版即覆盖所有非权限类阻塞类型

## 当前实现状态

### 已完成能力

系统已经具备以下能力，主链路不再停留在“总管家只展示、不处理”的状态：

- 操作权限与 ACP 权限的待处理快照已持久化，并带有人类可读的 `review_code`
- 桌面端审批继续通过统一的 `confirm_operation_permission` / `confirm_acp_permission` 回写
- 飞书端已经具备权限审批桥接能力，包括卡片回调处理与关键词回复降级
- 内置工具 `task_conversation_operation` 已经加入 Butler agent 工具集
- `task_conversation_operation` 已支持 `read`、`reply_prompt`、`permission_confirm`、`operate_confirm`、`acp_permission_confirm`
- 当子任务出现待处理权限时，主 Butler 会话会收到 `<butler_task_attention>` 系统提醒
- Butler 系统提示词已经明确要求在收到阻塞提醒时优先使用 `task_conversation_operation`
- 相关定向 Rust 测试已经补齐并通过，覆盖了工具暴露与 attention 消息识别

### 当前仍未完成的部分

距离“总管家自动处理权限请求”的最终目标，还差以下三类能力：

1. **策略化自动决策层**
   目前总管家已经能主动读子任务、执行确认和发补充提示，但还没有形成一套显式、稳定、可配置的规则优先决策层。也就是说，主动处理框架已就位，系统化自动裁决策略还没有完整落地。

2. **更完整的阻塞类型覆盖**
   当前主打通的是权限请求场景，已经足以覆盖最关键的卡点。但“像人一样操作 task conversation”的完整能力还可以继续扩展到更多等待确认、执行分叉和非权限阻塞场景。

3. **端到端实战验收**
   代码层和定向测试已经通过，但还需要在真实运行中确认：子任务发起权限请求后，Butler 会稳定地主动读取最新消息、做出处理、并让子任务继续推进。

### 完成度判断

如果以“人工审批多渠道可用”为目标，已经基本完成。

如果以“总管家真正成为处理主体”为目标，核心框架已经完成，主链路已打通。

如果以“规则完善、自动处理稳定、可覆盖大多数权限请求”为目标，目前还处在最后一段收口阶段。整体上可以认为：**基础设施和主动处理框架已经到位，距离最终版本主要还差策略层、覆盖面和实战验证。**

## 用户场景

### 目标用户

- 使用总管家派发复杂任务并希望任务自推进的用户
- 需要在受控目录或受控工具边界内长期自动执行任务的用户
- 希望在桌面外也能处理审批的飞书用户

### 使用场景

场景一：总管家派发代码整理任务，执行助手申请读取或编辑工作区内文件。总管家收到阻塞提醒后，查看子任务最新状态，确认请求符合当前任务目标并自动放行。

场景二：执行助手申请访问工作区外目录或高风险 ACP 选项。总管家判断超出安全边界，不直接放行，而是转为人工审批。

场景三：用户不在电脑前，权限请求转入飞书，用户通过卡片按钮或关键词回复完成审批，结果回写到原始等待链路。

## 功能详情

### 功能点一：总管家必须能操作现有子任务会话

总管家不能只有 `spawn_task_conversation`，还必须拥有查看和操作已存在 task conversation 的能力。这是当前方案的核心。

推荐做法是把总管家对子任务的操作面固化为一个统一工具：`task_conversation_operation`。总管家通过这个工具完成以下动作：

- 读取指定子任务会话的最新状态和最新消息
- 查看当前待处理的操作权限与 ACP 权限
- 对待处理权限直接执行确认
- 在子任务空闲但尚未结束时补充新的提示，推动其继续执行

这套操作面应默认使用最小上下文，优先只读最新 1 条消息，必要时再扩大到最近 2 到 3 条，避免主 Butler 会话被子任务历史淹没。

### 功能点二：总管家通过阻塞提醒触发主动处理

当子任务出现待处理权限时，系统不应依赖“在权限请求发起处等几秒让模型裁决”的短窗口逻辑，而应向主 Butler 会话注入一个结构化提醒，促使 Butler 主动进入对应子任务会话进行处理。

该提醒应至少说明：

- 哪个子任务被阻塞
- 当前阻塞类型
- 是否存在操作权限待处理
- 是否存在 ACP 权限待处理
- 子任务最新一条非系统消息摘要

Butler 收到提醒后，优先调用 `task_conversation_operation read` 查看详情，再决定是确认权限、补充提示还是继续等待。

### 功能点三：权限处理必须统一收口

无论结果来自 Butler 主动处理、桌面端人工审批还是飞书端人工审批，真正的权限结果都必须走同一组后端确认入口。

统一收口的好处是：

- 子任务等待逻辑不需要区分处理来源
- 桌面端与飞书端不会形成两套状态机
- Butler 主动处理与人工处理可以共享同一份待处理状态
- 后续增加审计、统计和策略时更容易扩展

因此，操作权限继续统一收口到 `confirm_operation_permission`，ACP 权限继续统一收口到 `confirm_acp_permission`。

### 功能点四：飞书必须作为人工处理兜底渠道

飞书人工审批不是可选附件，而是该方案的重要兜底能力。只要权限请求已经决定转人工，就应允许用户在桌面端或飞书端任一侧完成处理。

飞书侧当前应提供两层能力：

- **原生交互卡片**：适合作为默认体验，直接展示任务、权限摘要与可选动作
- **关键词回复降级**：当卡片不可用、链路不稳定或用户更偏好文字操作时，支持以审批号进行快速回复

推荐的关键词格式如下：

- 操作权限：`批准一次 OP-XXXXXX`、`本任务批准 OP-XXXXXX`、`助手批准 OP-XXXXXX`、`拒绝 OP-XXXXXX`
- ACP 权限：`批准 1 ACP-XXXXXX`、`批准 2 ACP-XXXXXX`、`取消 ACP-XXXXXX`

### 功能点五：自动处理仍需受安全边界约束

总管家成为处理主体，不等于总管家获得无限授权。自动处理必须始终受到任务边界、目录边界和风险级别的约束。

建议遵循以下原则：

- 仅允许在 Butler 父子任务作用域内操作 task conversation
- 默认优先一次性或对话级授权，而不是永久授权
- 工作区外访问、高影响写入、全局白名单变更等高风险操作优先转人工
- 任何自动处理结果都必须可追踪

## 业务规则

- `task_conversation_operation` 只能在 Butler 主会话或 Butler 子任务会话上下文内使用
- Butler 默认先读最新一条消息，只有在信息不足时才扩大读取范围
- 同一个待处理权限在后端只有一份真实状态，先成功提交的一方生效
- 飞书关键词审批必须带审批号，不能仅凭“批准”或“拒绝”生效
- 非当前会话链路用户的飞书回复不能直接生效
- 自动处理优先追求继续推进任务，而不是追求一次性给出永久授权

## 架构设计

### 整体架构

推荐采用“子任务阻塞 -> Butler 主动接手 -> 统一确认入口回写”的架构，而不是“权限请求产生时立即在后台短等待自动裁决”的架构。

整体链路如下：

`子任务触发权限请求 -> 后端保存待处理快照 -> 发送桌面/飞书人工提醒 -> 注入 <butler_task_attention> -> Butler 使用 task_conversation_operation 读写子任务 -> 统一 confirm_* 回写 -> 子任务继续执行`

这个架构保留了原有等待通道，同时把“真正的处理动作”上移到总管家运行时。

### 总管家与子任务的交互方式

推荐的职责划分如下：

- **子任务会话**：权限请求和阻塞状态的发起方
- **主 Butler 会话**：总管家的决策入口，负责收到提醒后决定下一步动作
- **task_conversation_operation**：主 Butler 操作子任务的统一控制面
- **待处理权限状态池**：后端保存待审批快照和 review code 的唯一真实状态
- **桌面端与飞书端**：人工兜底入口，不持有权限最终状态

该设计的关键点是：总管家不需要把子任务完整历史复制到自己上下文里，而是通过工具随取随看、按需操作。

### task_conversation_operation 的能力边界

该工具应长期稳定支持以下动作：

- `read`：读取任务详情、运行状态、最近消息和待处理权限摘要
- `reply_prompt`：对子任务补充新的提示
- `permission_confirm` / `operate_confirm`：确认操作权限
- `acp_permission_confirm`：确认或取消 ACP 权限

未来如需扩展，也应继续沿着“像人一样操作 task conversation”的方向增加动作，而不是回退到只靠短时间后台裁决。

### 飞书人工审批路径

飞书审批应与桌面端并行存在，但两端都不应各自持有审批状态。推荐链路如下：

- 后端保存权限快照并生成审批号
- 若该任务具备飞书链路，则向飞书发送审批卡片或回退文本
- 飞书卡片回调或文本解析后，仍然调用统一 `confirm_*` 接口
- 一旦任一渠道处理成功，其他渠道自动看到“已处理”结果

这样飞书只是另一个入口，而不是另一套审批系统。

## 技术方案

### 推荐方案

推荐采用以下组合方案：

1. **现有信任判断优先**
   保留本地白名单、会话信任路径、助手工作区等已有确定性判断。

2. **Butler 主动处理作为主链路**
   当子任务进入权限阻塞时，由主 Butler 收到 attention 后主动读取和处理，而不是在请求发起点依赖一个短时间模型裁决窗口。

3. **规则优先的自动化策略作为下一阶段增强**
   在当前主动处理框架之上，继续增加明确的低风险规则，减少对模型自由判断的依赖。

4. **桌面端与飞书端人工兜底**
   对于高风险、不确定或暂不支持自动处理的场景，继续保留人工确认。

### 为什么不再采用短窗口自动裁决

短窗口自动裁决能处理一部分简单情况，但它有三个问题：

- 处理动作发生在请求发起点，无法覆盖更丰富的子任务状态
- 无法让总管家像人一样查看并操作既有 task conversation
- 容易把“总管家处理”退化成一段不可见、不可控的后台猜测逻辑

因此，当前推荐路径不再把它作为主方案，而是以主动操作 task conversation 为核心。

## 非功能需求

- **安全**：自动处理不能突破 Butler 父子任务边界，不能绕过既有高风险限制
- **可追踪**：所有权限请求都应能追踪来源、处理方式和最终结果
- **低噪声**：Butler 提醒应去重，避免主会话被重复阻塞通知淹没
- **可恢复**：任意一个人工渠道处理成功后，其他渠道应能正确感知已处理状态
- **可扩展**：后续可以继续增加更多 task conversation 操作，而不必重构整体思路

## 分阶段落地

### 第一阶段：主动处理框架与人工兜底

这一阶段的目标是让总管家真正具备处理能力，而不是只展示权限请求。范围包括：

- 待处理权限快照与审批号
- `task_conversation_operation`
- Butler attention 提醒与主动回流
- 桌面端审批统一回写
- 飞书卡片审批与关键词降级

这一阶段的大部分核心能力已经到位。

### 第二阶段：策略化自动处理

这一阶段的目标是让“主动处理”进一步升级为“稳定自动处理”。范围包括：

- 规则优先的低风险自动放行策略
- 高风险自动转人工的明确边界
- 更结构化的决策理由与审计信息
- 更稳定的端到端运行验证

### 第三阶段：阻塞场景扩展

在权限处理稳定后，再沿同一思路扩展到更多子任务阻塞类型，让总管家在更多情况下都能像人一样接管 task conversation。

## 验收标准

- [ ] 子任务触发操作权限后，Butler 能收到阻塞提醒并主动读取子任务最新状态
- [ ] Butler 能通过 `task_conversation_operation` 直接确认操作权限并让子任务继续执行
- [ ] Butler 能通过 `task_conversation_operation` 直接确认 ACP 权限并让子任务继续执行
- [ ] 桌面端与飞书端都可以作为人工审批入口，并统一回写到同一条等待链路
- [ ] 飞书交互卡片不可用时，用户可以通过审批号关键词完成处理
- [ ] 高风险或策略外请求不会被默认自动放行
- [ ] 整个链路具备可追踪性，能区分 Butler 主动处理与人工处理

## 结论

目标没有变化：总管家依然要成为权限请求的实际处理者。

当前变化的是实现路径。系统已经不再以“短时间自动裁决”作为主方案，而是以“总管家主动查看并操作子任务会话”作为核心设计。这个方向更符合你对“总管家像人一样处理子任务”的要求，也更适合后续继续扩展到更多阻塞场景。
