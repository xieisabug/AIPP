# AIPP 多端同步方案复盘与替代路线评估

## 1. 背景

这份文档用于复盘 AIPP 当前自建同步方案为什么跑不通，以及给出下一步更现实的技术路线。

当前目标很明确：

- AIPP 是桌面端应用，Rust 后端，客户端本地数据仍然主要落在 SQLite
- 希望支持多设备同步
- 最好支持自建部署
- 最好不要把所有数据都强依赖在线中心库

## 2. 当前方案为什么失败

当前 AIPP 代码里使用的是 `libsql = 0.9`，锁定到 `0.9.30`：

- `src-tauri/Cargo.toml`
- `src-tauri/Cargo.lock`

代码中的同步模式是 `libsql::Builder::new_synced_database(...)`，本质上依赖旧版 libsql synced database 协议。

### 2.1 AIPP 当前客户端依赖的协议

现有 libsql 0.9.30 客户端会请求这类旧同步端点：

- `/info`
- `/export/<generation>`
- `/sync/...`

而 AIPP 当前会把用户填写的同步地址继续拼成：

- `/dev/system`
- `/dev/conversation`
- `/dev/artifacts`

也就是说，如果用户配置的是：

```text
http://server:9000/t/<tenant_uuid>
```

那么 AIPP 最终会去请求：

```text
http://server:9000/t/<tenant_uuid>/dev/system/info
```

然后 gateway 再把它转成上游 sqld 根接口。

### 2.2 实际验证结果

在服务器上的实际验证结果已经很清楚：

- `GET /t/<uuid>/dev/system/info` -> `404`
- `POST /t/<uuid>/dev/system/v2/pipeline` -> `200`

这说明：

- tenant token 正常
- gateway 路由正常
- namespace 也正常
- 裸 sqld 本身也能正常响应 pipeline API

失败原因不在部署细节，而在**协议不兼容**。

### 2.3 为什么不兼容

公开可见的官方 `libsql-server` 镜像路由（包括 `latest`，以及 GHCR 上还能看到的 `v0.22.x`、`v0.23.x`）已经是：

- `/v2/pipeline`
- `/v3/pipeline`
- `/dev/:namespace/v:version/pipeline`

而不再提供：

- `/info`
- `/export`
- `/sync`

所以当前这条方案的真实情况是：

- AIPP 客户端使用的是 **旧同步协议**
- 官方自建 `libsql-server` 镜像已经转到 **新协议**
- 两边并不兼容

## 3. 结论：当前 libsql 自建方案是否还能救

结论是：

**不建议继续把当前自建 libsql/sqld 路线作为正式方案推进。**

理论上能想出来的“补救”方法有三种：

### 3.1 固定更老的 libsql-server 镜像

问题：

- 我已经确认 GHCR 上公开保留的 `v0.22.x / v0.23.x` 也没有旧同步端点
- 没有证据表明存在一个仍然受维护的、兼容旧协议的官方 LTS 镜像
- 即便找到更老镜像，也大概率没有持续安全维护

结论：

- 只适合作为一次性排障实验
- 不适合作为正式方案

### 3.2 自己写协议兼容层

也就是自己实现一层服务，把旧的：

- `/info`
- `/export`
- `/sync`

翻译成新的 pipeline 协议。

问题：

- 这相当于自己维护一套数据库同步协议
- 风险不是“代码麻烦”，而是“数据正确性和恢复语义很容易出错”
- 一旦出问题，不是小 bug，而是同步损坏、数据漂移、冲突不可恢复

结论：

- 不建议

### 3.3 升级 AIPP 到新的 libsql 客户端

这条理论上最像“原地修复”，但风险也不小：

- 需要先确认新的 Rust `libsql` 客户端是否真的支持当前自建服务端的同步语义
- 即便 crate 还在发版，也不等于它的“自建 embedded sync + 自托管 sqld”路径仍是官方主推方向
- 现有证据表明，这条产品路线已经明显不是主流路径

结论：

- 可以作为一次技术验证方向
- 但不适合作为当前项目的主要押注方向

## 4. 更现实的替代路线

如果目标仍然是：

- 客户端继续保留本地 SQLite
- 支持多端同步
- 方案最好是现在还在推进的

那么当前更现实的路线只剩两类。

### 4.1 路线 A：PowerSync

这是目前我看到最接近“现成、现代、仍在维护”的路线。

#### 公开定位

PowerSync 明确主打：

- 服务端数据库与客户端嵌入式 SQLite 同步
- local-first / offline-first
- 客户端 SDK 支持多平台
- 官网公开展示了 Tauri / Rust 客户端支持

它的模型不是：

```text
SQLite <-> SQLite 文件级同步
```

而是：

```text
服务端数据库 -> PowerSync 服务 -> 客户端本地 SQLite
```

支持的服务端数据库包括：

- PostgreSQL
- MySQL
- MongoDB
- SQL Server

#### 优点

- 明显还在推进
- 很贴近 AIPP 的最终目标：客户端继续本地 SQLite
- 不需要继续赌半废弃的 sqld 自建同步协议
- 已经是专门做 sync engine 的产品形态

#### 缺点

- 服务端不是完全自由开源：客户端 SDK 开源，但服务端是 source-available
- 架构上要接受“远端主数据源”不是 sqld，而是别的后端数据库
- 对现有 AIPP 同步实现不是小修，需要切换同步栈

#### 对 AIPP 的改造含义

如果走 PowerSync，AIPP 更合理的做法会变成：

- 客户端仍然是 SQLite
- 远端改成 PostgreSQL 优先
- 服务端由 PowerSync 负责变更捕获、下发、写回协调

这意味着：

- 需要重新定义哪些表是“同步表”
- 需要提供服务端数据库 schema
- 需要把原本 SQLite-only 的一些本地状态和云端状态分层

但这条路线仍然比继续修 libsql 方案更现实。

### 4.2 路线 B：自研应用层同步

这是最不依赖第三方命运、也最稳的一条工程路线。

核心思想是：

- 本地继续用 SQLite
- 不再尝试同步整个数据库或依赖底层数据库专用协议
- 只同步业务层变更

典型做法：

- 每张需要同步的表都有稳定主键
- 增加 `updated_at`
- 增加 `deleted_at`
- 增加版本号或逻辑时钟
- 写操作同时记录到 `oplog` / `changes` 表
- 服务端保存全量变化日志
- 客户端按游标拉增量、推本地变更

#### 优点

- 完全可控
- 不会被某个外部同步库的路线变化卡死
- 业务语义最清晰
- 自建最自然

#### 缺点

- 需要自己设计冲突规则
- 需要自己明确哪些数据该同步、哪些不该同步
- 前期工程量比“接一个现成 SDK”更大

#### 对 AIPP 的意义

其实 AIPP 非常适合这条路线，因为它的数据天然就分层：

- 会话/消息/工件 适合同步
- 模型缓存、临时状态、设备级配置 不一定适合同步
- 部分本地索引和派生状态可以重建，不必同步

换句话说，AIPP 并不一定需要“整库同步”，更需要的是“核心业务数据同步”。

### 4.3 路线 C：Electric

Electric 是明显还在推进的同步基础设施，但它更偏：

- Postgres-first
- Web / TypeScript 生态更成熟
- 本地可嵌入 PGlite

对 AIPP 来说它的问题是：

- 它不是围绕 Rust + 原生 SQLite 桌面端做的最顺滑路线
- 更像要重新围绕 Postgres 思维重构同步架构

所以 Electric 可以关注，但不是我对 AIPP 的首推。

### 4.4 为什么不推荐 LiteFS / rqlite / dqlite 作为主路线

这些方案更偏：

- 服务端高可用
- 单写主库复制
- 集群一致性

它们不擅长解决的，是 AIPP 这种核心问题：

```text
两台桌面设备都能离线写，
然后重新联网后再把数据合并。
```

所以它们不是最对症的方案。

## 5. 对 AIPP 的推荐

### 5.1 推荐结论

如果要求是“尽快找到一个还在维护的现代方案”，我的推荐顺序是：

1. **PowerSync**
2. **自研应用层同步**
3. **Electric（仅作为备选观察对象）**

### 5.2 如果追求最快落地

推荐：

**PowerSync + PostgreSQL + 客户端 SQLite**

适合条件：

- 接受服务端不再是 sqld
- 接受引入 PostgreSQL 作为远端主库
- 接受服务端不是完全 OSI 开源，而是 source-available

### 5.3 如果追求长期可控

推荐：

**本地 SQLite + 自研 oplog / changes sync**

适合条件：

- 不希望把核心命运压在外部同步厂商/项目上
- 愿意多做一点应用层设计
- 更重视长期控制权和可解释性

### 5.4 我对当前方案的最终判断

当前 `libsql 0.9.30 + 自建 sqld` 路线，不应该再继续作为正式方案投入。

原因不是“今天没调通”，而是：

- 技术基础已经分叉
- 官方公开可用的 server 镜像协议不匹配
- 没有明确可信的兼容 LTS 路径
- 继续修复的收益远低于切换路线

## 6. 建议的下一步

建议按下面顺序做：

### 方案一：PowerSync 预研

需要回答的问题：

- AIPP 现有 SQLite 表里，哪些应该进入远端主库
- PostgreSQL 端应该如何建模
- 客户端 SQLite 中哪些仍然保持纯本地
- PowerSync 的 Rust/Tauri 集成方式是否满足 AIPP 的运行形态

### 方案二：自研应用层同步设计

需要明确：

- 哪些表同步
- 每张表的冲突策略
- 删除语义如何处理
- 首次同步如何处理
- 设备 ID / 变更游标 / 版本时钟如何设计

## 7. 当前建议

如果明天要继续推进，我建议优先做：

1. 出一版 **AIPP 基于 PowerSync 的落地方案**
2. 再出一版 **AIPP 自研应用层同步架构设计**

然后在这两条路线之间做决策。
