# 定时任务

定时任务模块用于让普通对话助手在后台按计划执行任务。它既能做固定时间触发，也能做按间隔循环执行，并且完整记录运行日志、执行结果和通知决策。

---

## 定时任务的基本模型

### 当前支持的调度类型
- `once`：一次性任务，在指定时间执行一次
- `interval`：按固定间隔重复执行

### 当前支持的间隔单位
- `minute`
- `hour`
- `day`
- `week`
- `month`

### 时间配置能力
- 一次性任务使用 `run_at`
- 日 / 周 / 月间隔任务支持 `start_time`
- 周任务支持 `week_days`
- 月任务支持 `month_days`
- 创建或更新任务时，后端会立即计算 `next_run_at`

> 当前实现不是 Cron 表达式编辑器，而是“调度类型 + 间隔单位 + 时间字段”的结构化配置。

---

## 任务创建与管理

### 基础管理 API
- `create_scheduled_task`
- `update_scheduled_task`
- `delete_scheduled_task` - 同时清理日志和运行记录；清理失败时整体回滚。删除后仍在结束中的执行不会重新写入无主的日志或运行记录。
- `list_scheduled_tasks`

### 任务字段
- 任务名称
- 启用 / 禁用状态
- 执行助手 `assistant_id`
- 主任务提示词 `task_prompt`
- 通知判定提示词 `notify_prompt`

### 助手约束
- 只能选择**普通对话助手**
- 如果助手没有模型或没有系统提示词，运行会直接失败并写入日志

## 调度与执行

### 下次执行时间计算
- `compute_next_run_at_with_config` 负责根据当前时间和调度配置计算下一次执行时间
- 一次性任务在执行后会自动失效
- 间隔任务执行后会刷新 `last_run_at` 和 `next_run_at`

### 立即运行
- `run_scheduled_task_now` 可手动立即触发任务
- 即时运行仍然会写入运行记录和日志
- 对一次性任务来说，手动运行后同样会被自动关闭

### 后台执行模型
- 每次运行都会生成唯一 `run_id`
- 任务会创建独立的执行对话，由助手在其中完成任务
- 执行链路支持：
  - 模板引擎
  - Slash 提示词解析
  - MCP 工具
  - 已启用 Skills

---

## 运行状态、日志与停止

### 运行记录
- `list_scheduled_task_runs` 返回任务的运行历史
- 运行记录包含：
  - `status`
  - `notify`
  - `summary`
  - `error_message`
  - `started_time`
  - `finished_time`

### 日志记录
- `list_scheduled_task_logs` 返回详细日志
- 日志会记录开始执行、工具调用情况、模型输出、通知判定、清理动作、停止请求等关键节点
- 前端通过事件 `scheduled_task_log_added`、`scheduled_task_run_created`、`scheduled_task_run_updated` 实时刷新

### 停止运行中的任务
- `stop_scheduled_task_run` 可停止当前正在运行的执行记录
- 内部通过 `CancellationToken` 实现取消
- 收到停止请求后会写入 `cancel_request` 日志，并尽量安全终止执行
- 等待模型回复期间也能停止；停止后不会再按完成处理，失败原因会注明已执行的工具次数及“已产生的外部操作无法撤回”

### 运行保护
- 当前内置了 agentic loop 安全限制：
  - 最大轮次：50
  - 单次工具调用超时：120 秒
  - 总执行超时：3000 秒
- 取消、超时、达到最大轮次、模型错误等都会写入日志并落到失败结果（`error_message` 写明具体原因），不会进入通知判定，也不会记为成功
- 应用在执行过程中退出时，重启后会把遗留的“运行中”记录标记为失败（结果未知），不自动重跑

## 通知决策与结果处理

### notify_prompt 的作用
- 任务完成后，并不会无条件通知用户
- 系统会把执行报告交给模型，再结合 `notify_prompt` 决定：
  - 是否需要通知
  - 要给用户展示什么简洁结论

### 两种收尾方式
- **需要通知**：
  - 保留对话
  - 对话标题会更新为 `计划任务: {任务名}`
  - 触发系统通知，引导用户查看结果
- **不需要通知**：
  - 自动清理本次执行对话
  - 仍保留任务运行记录与日志，便于排查

### 通知判定失败
- 通知判定模型调用失败、超时或返回不合法时，只影响是否通知：执行结果仍按实际完成记为成功，并保留本次对话供查看

### 管家绑定任务的结果回报
- 管家创建或绑定的任务，每种结束原因（成功、失败、停止、超时、轮次耗尽、启动前失败、应用退出中断）都会回报总管家主会话，回报中带 `status`、`end_reason` 与具体错误
- 回报状态记录在 `butler_followup_status`（pending → continuing → done / failed），不改写执行结果；主会话忙碌或有用户消息排队时持续排队，不抢占会话
- 只有总管家对该结果出现自然完成的回复才记为 done；回报前或续跑中途应用退出时，重启后按 run_id 补报且不重复注入结果

### 最终结果
- 对外返回 `RunScheduledTaskResult`
- 结果中包含：
  - `success`
  - `notify`
  - `summary`
  - `error`

---

## 适合文档层面的理解

- 定时任务更像“后台代办助手”，不是单纯的 cron 命令
- 真正决定用户是否会被打扰的，不是任务有没有跑完，而是 `notify_prompt` 的判定结果
- 即使没有通知用户，系统仍然保留运行历史与日志，便于审计和调试

## Android 本机任务页

移动设置中的“本机任务”列出计划及运行记录。`本机执行中` 以当前进程的运行令牌为准；同步来的 `running` 历史但没有本机令牌时显示“结果未知”，不提供远程停止。可在本机手动运行一次，助手及工具依赖会先校验，正在本机运行的同一任务不能重复启动。

应用首次扫描前已到期的任务记为 `missed`，不补跑、不报告成功；一次任务关闭，周期任务推进下一次计划，保留最近真实执行时间。多个错过周期合并记录为最早尚未处理的一次到期时间。应用仍存活时由进程内调度器运行，不承诺锁屏、系统挂起或退出后的持续执行。移动任务页不替代桌面完整计划编辑器。
