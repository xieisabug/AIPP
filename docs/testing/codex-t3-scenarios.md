# Codex t3 scenario inventory and AIPP unified-use scope

Reference: `t3code` commit `d5fc29fe5cb62db68bfbf824cfabe0ae94ac6ac4`, `apps/server/src/orchestration-v2/Adapters/CodexAdapterV2.test.ts`. Line references below are fixed to that commit, not the AIPP checkout. Inventory extracted by parsing TypeScript call expressions, not by counting Rust test names.

## Scope and evidence rules

The requested work is the **unified agent-use boundary and its existing lifecycle guarantees**, not implementing every provider-specific t3 capability. AIPP intentionally keeps separate per-conversation Codex actors; it does not adopt t3's shared process, continuation, native-child, fork, goal, or MCP-app architecture.

- **Covered** means a named production-path test proves the applicable scenario. A passing mapper/helper alone cannot establish actor/session-loop coverage.
- **Gap** means the common guarantee applies but the cited existing evidence is partial or absent. Missing native end-to-end coverage remains a gap even when a narrower transport regression exists.
- **Excluded** means the exact t3 scenario is unsupported, architecture-specific, provider-specific, or explicitly outside the user's narrowed scope. Excluded does not mean implemented, tested, or safe by default. A neighboring common AIPP contract is called out separately when useful.

All 81 static registrations are listed once. Static expansion of the parameterized declarations derives 145 cases (61 ordinary registrations plus 20 `.each` registrations expanding to 84 cases). The t3 runner was not executed; this is a source-derived expansion rather than an observed runtime count. Internal loops are described where semantically relevant and do not increase the static-registration count. This is an inventory, not a coverage percentage or a numerical target.

Paths used below: native tests are in `src-tauri/src/api/ai/codex_app_server.rs`, `codex_app_server_lifecycle_tests.rs`, `codex_app_server_permission_tests.rs`; unified tests are in `src-tauri/src/api/ai/agent_driver/{session,dispatch}_tests.rs`. Native inline tests predate this work; new tests remain in separate domain files.

## Implementation limits and validation

- Existing Wry-bound `run_session`, real desktop events and file-backed `ConversationDatabase::new` are deliberately not instantiated in these tests. No persistent DB is opened. Permission fixtures are in-memory; unified dispatch fixtures use `Connection::open_in_memory()`.
- The fake peer executes only a fixed JSON transcript over real child pipes, not an alternate session algorithm. Temporary files contain only that fixture script. Protocol tests require Unix and `python3`; other platforms do not compile this Unix-only module. Existing cross-platform control/permission tests still run.
- Async waits are bounded. The fake subprocess uses production `kill_on_drop(true)`; successful paths close stdin and wait/reap the child. A panic/timeout drops and kills the child. Tests do not contact a network, real Codex account, user workspace, or credentials.
- Red phase was actually executed before adding cancellation observation to the extracted production waiter: `test_codex_unified_cancel_unblocks_permission_wait_without_cancelling_peer` failed at its 500 ms timeout (0 passed, 1 failed), confirming the original blocked-wait behavior. Parent-run log: `tmp/worklog/alignment-codex-red.log`.
- Final green validation after the happy-resume fixture correction: all **58 Codex-module tests passed**, including all 8 new transport tests and 4 new interaction/cancellation tests; 0 failed/ignored. Log: `tmp/worklog/alignment-codex-final.log`. Parent also ran `cargo check` successfully and final scoped driver (28), ACP (41), Claude (39), and idle-session (3) suites; total 169 scoped Rust tests passed. Validation was serial in the repository's default target directory. These are scoped results, not a full repository or t3 suite, live CLI authentication, or Windows/macOS subprocess run.
