# 管家协作群 PRD

需求：#284（群与上下文）、#282（发言调度），执行任务 #588。

## 产品定位

用户与总管家、受邀助手围绕同一目标交流和协作。群保存公共发言，每个成员拥有独立的群内上下文。用户直接与承担工作的成员沟通，不要求每次发言都创建任务。独立任务仅用于需要单独上下文、长期执行或同一成员并行处理的工作。

范围限于桌面管家；不包含外部渠道接入、多真人账号和长期记忆系统扩建。

## 上下文与缓存

可见、接收、回应分别管理。可见表示有权读取；接收表示资料已进入模型输入；回应表示存在明确待处理事项。投递位置不能代替回应状态。

每个成员的模型消息链只追加。固定身份和基础规则保持稳定，群目标、成员变动、能力变化作为新增事件进入尾部。已投递的正文、时间、顺序和包装文字不再重写。成员工具定义保持稳定，不随其他成员状态反复变化。

每次激活固定公共消息上界，读取该成员获准但尚未投递的内容，补齐指定引用，形成不可变输入包。成功写入成员上下文后推进投递位置；重试复用原输入包。自己已经生成的公开发言不重复注入正文。其他成员发言是外部资料，不作为本人的 assistant 历史。

私聊与其他群的消息、摘要、执行会话均不继承。新成员默认仅看到加入后的公共消息和用户明确分享的旧内容。重新加入创建新的成员资格。用户分享必须指定资料和范围；引用不绕过权限。

## 公共内容与工具过程

群记录用户发言、成员公开观点、进度、交付、问题与状态。工具参数、原始工具结果、思考内容和内部调度记录只属于执行成员。需要共享证据时明确发布附件、摘录或结果引用。

流式展示不等于可投递记录。只有已提交的完整公开消息进入其他成员的输入；后续修正作为新消息，不修改已投递原文。

## 回应规则

| 事件 | 回应者 |
|---|---|
| 用户普通发言 | 总管家 |
| 用户明确点名 | 被点名成员 |
| 顺序征求意见 | 当前轮到的成员 |
| 定向回复 | 明确接收成员；用户回复默认指向原作者 |
| 明确协作委托 | 受托成员 |
| 普通观点、进度、公开结果 | 不额外唤醒成员 |
| 已登记等待的结果返回 | 等待该结果的执行 |
| 回答问题、批准 | 原问题或批准所属执行 |
| 停止 | 程序立即处理，不等待模型理解 |

引用资料与定向回复分开。输入框显示回复对象，后台保存稳定成员及消息身份。正文、引用、代码块中的名字不构成点名。一次触发对同一成员只建立一个回应事项。完成回执不成为新委托，不自动制造感谢循环。

助手明确回复上游原消息时，回应路由到原消息所属执行；原作者在独立任务中发言的，回复仍进入该任务。回复保留原输入包归属，不算向上游重新派工，不增加委托层级；仍计入原工作链派发预算。仅引用资料不获得这一回应语义。需要上游再执行工作并等待其结果时，按新委托检查循环，不借回复关系绕过限制。

## 顺序讨论

总管家理解自然语言后提交结构化发言安排。用户指定顺序优先，否则使用群成员展示顺序。每人默认一个席位，不自动开启第二轮，不强制汇总。

轮到成员时才固定其输入上界，保证后发言者看到前面已提交的意见。先发言者不会因后续意见自动再次启动。用户要求独立判断时，各成员使用同一个公共消息上界，与顺序讨论分开处理。

独立判断的上界同时约束工具补读、搜索与引用，不能通过补读看到后续意见。该上下文存在未完成的独立判断时，暂停再派群协作、讨论、子任务及读取任务动态，避免其他执行回送快照之后的资料；仍可使用自身工具完成判断并公开交付。独立事项结束后解除这一限制。

执行结束并交付公开回答才完成席位，开始工作或工具进度不算完成。等待用户、等待批准时释放席位并保留未完成状态；超过可配置的等待期限也释放席位但不自动取消执行。后续成员看到等待事实。迟到结果正常发布，不自动重开结束的席位。失败、超时、不发言分别记录，部分完成不显示整体完成。

## 执行中消息

普通旁观消息留在公共日志，下次激活时接收。定向回复、当前工作的补充和依赖结果进入成员收件箱，在安全边界追加。停止、撤销批准和明确替换要求先更新执行约束，禁止旧执行继续提交。

安全边界必须保持工具调用与结果配对，不能在未完成的工具批次中插坏协议。原生通道支持中途投递时使用该能力，否则显示待送达，在原会话可接收时发送；不切换模型、provider、协议或新会话。消息到达时若最终回答已在生成，保留待回应事项，不能假称已经影响该回答。

## 回应、批准与停止

助手发起的定向消息、讨论席位、等待协作与独立子任务共享工作链派发约束：一条原始工作最多累计派出 32 项、最多派生 8 层，派发窗口从原始输入包创建时起计两小时。结果续接与子任务沿用该预算及期限，成功、失败和取消均不返还已使用的派发次数，幂等重试不重复计数。多个原始工作合并处理时采用合并后的累计用量及最早期限，不借合并重置预算。期限限制新增派发，不代表已发生的操作被撤销，也不宣称当前运行已经停止。用户明确发起独立的新工作使用自己的工作链。

待回应事项经历待投递、已投递、处理中、已回应，或进入等待、失败、取消、被新要求取代状态。每次输入明确区分背景消息和本次必须处理的事项。

问题、批准绑定群、成员、原请求、执行、版本和有效期。其他成员的文本不能代表用户批准；无关发言不应使其他工作的批准失效。只恢复被回答的问题所属执行。

停止成员工作仅影响本群选定工作及派生执行。整群停止先封住新派发，再逐项取消；单项失败不阻止其余取消。已发生的外部操作不宣称撤销。迟到结果只补记录，不恢复被取消工作。成员退出撤销后续读取和投递资格，并停止本群未完成工作。

停止传播沿明确派发、讨论席位、结果续接和子任务归属进行；回复上游不把上游当成下游任务。接收成员尚未接收的无关消息保留排队。若不同事项已合入同一模型输入包，停止其中派生工作时必须中断该输入包，并明确标记同包未完成事项受影响，不擅自重放工具。尚未投递的混合包可撤销并把无关事项退回队列，解除旧的未投递续接绑定。停止已投递的续接时同步结束原工作的等待状态。

## 长历史与恢复

正常情况下提供尚未接收的获准公共正文。超出预算时保留触发消息、指定引用和最新要求原文；较早背景可形成带来源范围的新增摘要，明确区分原文投递与摘要覆盖。原文可按权限补读。成员自身消息链仅在达到压缩阈值时建立 checkpoint。

背景摘要调用前先预留必读原文、引用和来源元数据所占空间，再按剩余输入预算分配各分片摘要额度，包含 JSON 转义开销。摘要写入时检查该额度，不覆盖已经保存的摘要。若必读内容与来源信息本身占满预算，则明确报错并保留未投递状态，不截断用户要求、不推进读取位置。

重启后恢复成员、投递包、回应事项和结果。已保存结果可以重新通知界面，但不得重复显示或重做工具操作。投递结果未知时显示待核对，不自动重复执行。原生恢复失败保存原始环节、底层原因和会话/执行标识。

## 界面

建群填写目标并选择成员，从管家任务列表重新进入。群内展示成员身份、公开发言、回应对象、等待状态、问题和批准。成员详情展示本群能力摘要，工具配置与实际可用性分开说明。提供定向回复、顺序讨论、分享历史、停止成员工作和停止整群入口。

## 验收

1. 三个成员依次发言：后者看到前者，前者不自动重新启动。
2. 同一成员在私聊和两个群的模型输入、搜索、引用、摘要互不泄漏。
3. 两成员并发工具执行，各自上下文不包含对方工具调用和结果。
4. 定向回复进入正确成员的收件箱，并关联原消息；仅引用资料不唤醒原作者。
5. 背景已投递不等于已回应，失败投递不推进位置，重试不重复追加。
6. 连续请求的既有消息前缀保持一致；目标和成员变更只追加。
7. 工具执行中收到回复，在安全边界送达；旧要求不能越过版本检查交付。
8. 等待问题或批准不阻塞无关成员；过期答案不能恢复其他执行。
9. 停止本群成员不影响其他群；一个取消失败仍尝试取消其他成员。
10. 重启后结果展示一次，未知投递不自动重做；取消后的迟到结果不复活任务。
11. 长历史摘要保留可追溯范围；新增成员不能通过摘要读到未授权历史。
12. 普通聊天权限及既有联系人行为无回归。
