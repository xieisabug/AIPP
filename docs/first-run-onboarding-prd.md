# 首次使用引导 PRD

状态：已实现，待桌面真机与真实账号验收（2026-11-25）。设计草图在作者的 Obsidian 笔记 `学习/Excalidraw/AIPP引导配置设计`。已确认的决定见第 19 节。

## 1. 为什么要做

### 1.1 新用户现在看到什么

全新安装后第一次打开 AIPP：

1. 首页是 **Ask 小弹窗**：`experimental.default_home_window` 没有值时回落到 `ask`（`window.rs::preferred_home_window_label`）。这是 800×450 的单轮问答窗口，没有任何配置入口。全局快捷键打开的也是它。
2. 新库的提供商列表为空。旧库可能保留禁用的内置提供商。
3. 「快速使用助手」（id=1）没有绑定模型。
4. 唯一的提示是聊天窗口新对话页的 `SetupGuideNotice`，Ask 弹窗里看不到。
5. 想用管家，要从托盘打开「总管家（实验）」，再走 5 步总管家设置向导。
6. 没有人告诉用户还要配轻量模型和审核模型。不配的后果分散在各处，见 1.2。

### 1.2 结构性问题

| 问题 | 现状 |
|---|---|
| 没有「新用户」概念 | 没有首次启动标记。`newChatSetupGuide.ts::resolveSetupGuide()` 只在新对话页判断；全新安装时它返回的是 `providers_disabled`，不是 `no_provider` |
| 配置门槛高 | 提供商、模型、轻量模型、审核模型、管家模型、工作区、bun/uv、Skills、插件分散在 6 个以上设置页，新用户分不清哪些是必须的 |
| 不配审核模型，管家处处要确认 | 管家会话强制使用模型审核（`butler_assistant_profile.rs`）。没配审核模型时，每次调用工具都要人工确认：HTTP 通道显示「自动审核失败，需要你确认」（`ButlerHeldToolCalls.tsx`、`ToolReviewNotice.tsx`），原生智能体通道显示「自动审核未完成，需要人工确认：自动审核模型未配置…」（`native_agents.rs`） |
| 对话总结无限重试 | 默认开启的对话总结任务每分钟运行一次。没有模型时报错但不写记录，下一分钟又挑出同一批对话，永远不停（第 12 节） |
| 本机智能体当不了总管家 | 总管家系统助手的类型写死为普通助手（`butler_assistant_profile.rs::sync` 写 `Some(0)`），`get_butler_model_selection` 又要求存在模型记录。只装了 Claude Code / Codex、没有 API 的用户用不了管家 |
| 分享码导入不完整 | `import_llm_provider` 只写 endpoint 和 Key，**不添加模型**，导入后新对话页立刻提示没有模型。它按名字反查新建的行，重复导入会建出多个「(导入)」，还可能拿错 id |
| 校验 Key 的报错不可读 | `preview_model_list` 直接返回 genai 的原始错误文本，状态码被丢掉，分不清是 Key 错、没网还是被限流。也没有「对聊天模型试调用一次」的命令 |
| 选择器列出用不了的模型 | 轻量、审核、调度等下拉框都用 `get_models_for_select`，会把有模型记录的本机智能体也列进去。选中后请求按 OpenAI 协议发往 `api.openai.com`，然后失败 |

## 2. 目标与非目标

**目标**

1. **第一次打开就有人带路**：新用户，以及「装了但从没配成功」的用户，启动时进入引导窗口，不再停在空白的 Ask 弹窗。
2. **躺平模式只需要提供一样东西**：一个 Key、一段分享消息，或一个已安装的本机智能体。其他按作者推荐自动配好：模型分工、管家、工作区、Skills、Office 插件、运行环境。
3. **专家模式只问必要的**：问到的每一项都让用户看到、可以改，其余留给设置页。
4. **安装不挡路**：下载和安装全部在后台进行，主模型配好就能开始用。
5. **只有本机智能体也能用**：总管家可以跑在本机智能体上；没有 API 模型时，各个后台小功能有明确、安静的退路，不报错，也不无限重试。
6. **不和同步冲突**：在别的设备用过 AIPP 的用户，可以在创建任何数据之前先登录同步。

**非目标（本期不做）**

- 移动端（Android）引导。移动端没有本机智能体，也装不了 bun/uv，以后单独做精简版。
- 一键搬家：整机迁移配置、Skills、插件和工作区文件，已记入后续规划。
- 从其他 AI 工具（Cherry Studio、ChatBox 等）迁移配置。
- 飞书接入。专家模式里只提示「以后在设置里接入」。
- 替用户登录 Claude Code、ACP、Pi、OpenCode、Kiro：它们目前都没有可以调用的登录状态接口（见 7.1.1）。
- 多语言。界面目前只有中文。

## 3. 核心概念

### 3.1 两种 AI 来源

| | 模型 API（DeepSeek、OpenAI、Anthropic API、中转站……） | 本机智能体（Claude Code、Codex、ACP、Pi、Cursor、OpenCode、Kiro、Antigravity） |
|---|---|---|
| 是什么 | 「租一个大脑」。AIPP 把问题、工具清单和记忆发过去，对方返回文字或工具调用请求，其余由 AIPP 完成 | 「请一个自带手脚的员工」。它是本机的另一个程序，有自己的大脑、工具和规矩。AIPP 启动它、交给它工作，它自己决定读什么文件、跑什么命令 |
| 一次调用 | 一两秒，按字数计费，可以同时发很多次 | 启动有开销（几秒到十几秒），消耗用户的订阅额度 |
| 能当主模型 | ✅ | ✅（普通聊天里作为 Agent 类型助手；当总管家需要第 11 节的改动） |
| 能当轻量模型 / 审核模型 | ✅ | ❌ |
| api_type | `openai_api`、`anthropic`、`deepseek` 等 | `acp`、`codex_app_server`、`claude_sdk`、`pi`、`cursor`、`opencode`、`kiro`、`antigravity`（`providerApiTypes.ts` 中 `kind: "local"` 的那些） |

判断一个提供商是不是本机智能体，**只看 api_type 在不在上面这份列表里**。新增 TS 函数 `isLocalAgentApiType()` 和 Rust 函数 `is_local_agent_api_type()`，两端共用同一份列表。不能复用智能体注册表的 `matches_provider` / `is_claude_code_provider`：`claude_sdk.rs` 里后者对 `anthropic` 也返回 true，会把 Anthropic API 误判成智能体。

### 3.2 术语与模型分工

本文统一使用以下三个术语。躺平模式的界面文案用括号里更口语的叫法：

| 本文术语 | 躺平界面叫法 | 设置页现有叫法 | 用途 |
|---|---|---|---|
| **主模型** | 主力 | 快速使用助手的模型 / 总管家模型 | 聊天和干正事 |
| **轻量模型** | 打杂 | 「默认轻量模型」（AI 与自动化）、「小型辅助模型」（总管家） | 起标题、对话总结、表单自动填写、MCP 摘要、管家进度总结、主动整理轻巡检、群聊调度（经回退链） |
| **审核模型** | 不单独展示（默认同打杂） | 「自动审核模型」 | 工具调用的安全审核（管家会话强制使用） |

引导写入的配置键：

| 写入项 | 配置键 | 格式 |
|---|---|---|
| 主模型（聊天） | API 绑定到助手 1；本机智能体绑定到 Agent 助手 | 新对话使用对应助手，Ask 固定使用助手 1（7.4） |
| 主模型（管家） | `experimental.butler_model_id` | `{code}%%{providerId}` |
| 轻量模型 | `conversation_summary.default_light_model` | `{code}%%{providerId}` |
| 审核模型 | `conversation_summary.auto_review_model` + `conversation_summary.auto_review_provider_id` | 专家模式分别存 code 和 provider id。躺平模式写入 `conversation_summary.default_decision_model`，工具审核沿用它。 |

审核模型**不会**回落到轻量模型。它的回退链是 `auto_review_model` → `default_decision_model` → 报错（`tool_review.rs::configured_review_model`）。其他后台功能的回退链都能落到轻量模型上，详见第 12 节。

### 3.3 本机状态

以下都存在**设备本地**的 `system_config` 表中。这张表不参与同步，现有的 `skills_migrated_to_agents` 这类本机标记也存在这里。需要新增读写命令。

| 键 | 含义 |
|---|---|
| `onboarding_state` | 无此键：没进过新版引导（包括从旧版本升级的用户）；`in_progress`：已选择路径、尚未完成；`completed`：已完成，或判定为老用户、同步过来的用户；`skipped`：已确认自己填写配置 |
| `onboarding_path` | `lie_flat`（躺平）/ `expert`（专家） |
| `onboarding_step` | 选路径后为 `path_chosen`；主来源等待充值时为 `awaiting_recharge`；准备好写入时为 `source_ready`，写完为 `applied` |
| `onboarding_draft` | 提供商 id 及归属（本次新建或复用）、模型分工及验证结果、待写入的选择。Key 仅保存在提供商凭据配置中 |
| `onboarding_completed_at` | 完成时间，用于排查 |
| `onboarding_setup_status` | 后台准备任务里每一项的状态（第 9 节） |
| `default_new_chat_assistant_id` | 新对话默认助手（7.4）。存在本机，因为助手 id 是本机编号 |

### 3.4 「可用来源」的定义

全文只用这一个定义：

- **API 提供商**：已启用；有 `api_key`，或者该类型本来就不需要 Key（例如 Ollama）；并且在 `get_filtered_models_for_select(0)` 的结果里至少有一个属于它的模型。
- **本机智能体提供商**：已启用，并且出现在 `get_filtered_models_for_select(4)` 的结果里（没有模型记录的智能体会补一行 `__agent_default__` 或 `acp`）。**严格判断**时还要求本机检测到它已安装。

有 Key 这一条很重要：同步过来的 API Key 是端到端加密的，必须输入同步口令才能解开（`sync/mod.rs`）。没解开之前，提供商虽然在，但用不了。

**快速判断**用在启动时，不做本机安装检测，保证启动不被拖慢。**严格判断**用在同步回来的数据上（4.6）。

## 4. 什么时候出现、什么时候不再出现

### 4.1 启动时的判断

只在桌面端（`#[cfg(desktop)]`）进行，在 `lib.rs` 打开默认首页**之前**判断：

```
本次 apply 写到一半 → 按 4.4 幂等完成同一次写入
管家模型与主工作区路径均已设置 → 记为 completed，打开默认首页
state = onboarding_state
completed / skipped → 正常打开默认首页
in_progress         → 打开引导窗口，按 onboarding_step 恢复（4.4）
无此键:
    快速判断有可用来源（3.4） → 静默写 completed，正常打开默认首页
    否则                   → 打开引导窗口，不打开默认首页
```

内置的 4 个禁用提供商不算可用来源。

### 4.2 各类用户

| 用户 | 结果 |
|---|---|
| 全新安装 | 弹出引导 |
| 装过但从没配成功（只有禁用的内置提供商，或者启用了但没有 Key、没有模型） | 弹出引导 |
| 旧版本升级，已有可用来源 | 不弹，静默写 `completed` |
| 管家模型和主工作区路径均已设置 | 启动、托盘、快捷键和手动入口都不再打开首次引导；以后在对应设置页调整配置 |
| 已确认自己填写配置 | 下次启动不会自动打开引导。手动入口见 4.5 |
| 中途退出 | 下次启动按恢复点继续（4.4） |
| 在引导里登录了同步 | 见 4.6 |

**引导进行中（`in_progress`）不会因为「出现了可用来源」而自动完成。** 引导自己就会创建并启用提供商，每次写入都会触发 `llm_provider_changed`。如果监听这个事件自动完成，引导会在第 7.2 节的配置写完之前就自己关掉。

### 4.3 关闭、跳过、托盘和快捷键

- **「我自己填」** 打开二次确认。默认聚焦「继续引导」，返回时保留当前步骤和输入。点击「确认自己填」后清理草稿（4.4），首次跳过时写 `skipped` 并打开聊天窗口（`chat_ui`）。之后不再自动弹出。
- **窗口右上角 ×**：只隐藏窗口，**不改变状态**。关掉窗口不等于做了决定，下次启动还会出现。应用照常留在托盘。
- **托盘左键**和**全局快捷键**按 4.1 判断。仅在本次应显示首次引导时打开该窗口，其余沿用原行为。托盘菜单里的其他项照常可用。
- **开机自启**：与正常启动一致，按 4.1 判断。
- **完成时**：引导窗口直接**销毁**，不是隐藏，避免它的事件监听一直留着。

### 4.4 中途退出与恢复

| `onboarding_step` | 下次启动 |
|---|---|
| `path_chosen` | 回到第 1 页（专家模式回到 8.1）。删除 `onboarding_draft` 里记录的、还没通过检查的草稿提供商（包括引导过程中导入的提供商） |
| `awaiting_recharge` | 保留用户选择保存的提供商和 Key。直接回到余额检查，允许充值后重新检查或改选来源；清理临时草稿时保留这条已保存的配置 |
| `source_ready` | 主来源已通过对应检查，模型分工已确定。继续执行 7.2；若上次已开始写入，则完成剩余写入，即使管家配置已在中途写好。恢复过程中不重新展示选项 |
| `applied` | 配置已经写入，`onboarding_state` 已经是 `completed`，不会再进入引导 |

- 草稿清理放在 Rust 侧、启动时执行，不依赖前端组件卸载。窗口只是隐藏的话，`NewProviderWizard` 卸载时那段清理代码根本不会运行。
- **配置写完（7.2）就写 `completed`**，不等用户点「开始使用」。这样用户在「好了」页点 ×，下次启动会直接进入首页，不会对一个已经配好的应用再弹一次引导。

### 4.5 重新打开（设置里）

「已配置管家」指总管家模型和主工作区路径均已填写。用户暂时关闭管家、提供商暂时不可用或工作区暂时无法访问时，仍保留这项判断。启动、托盘、快捷键和新对话提示共用此规则。设置齐全时，模型、首页和工作区都在各自设置页调整；后台准备任务可在聊天或管家窗口查看和重试。

桌面「设置 → 常规与外观」和新对话页的配置提示卡只在提供商和助手都未配置、管家也未配齐时显示手动入口。空的旧版内置提供商、未保存的引导草稿和未绑定模型的预置快速使用助手不计入配置。如果设备曾完成引导，清除配置后再从这里打开会进入**重跑模式**：

- 已完成的用户打开或取消重跑时保留 `completed`；此前跳过的用户主动继续后按 4.4 保存进度。
- 不删除任何已有数据，只覆盖本次明确写入的配置键。
- 写入前显示「将修改：默认首页、总管家模型、轻量模型……」，并注明「**这些设置会同步到你的其他设备**」（这些键和助手 1 都参与同步）。用户确认后才写入。
- 已经设置过主工作区的，**保留原来的路径**，不改成 `~/AIPP`。
- 已有管家模型时，更换其执行通道须先按 11.2 第 3 条确认。
- 已有同一 api_type 且已经填了 Key 的提供商时，推荐页提示「你已经添加过 DeepSeek，直接用它？」。

### 4.6 和同步的关系

现有规则：本机除了种子数据以外已经有数据时，第一次加入一个有数据的同步账号会被拦下（「本地和远端都已有数据…」，`sync/mod.rs`）。所以：

- 第 0 页、躺平第 1 页、专家 8.1 的底部，都有「在别的电脑上用过 AIPP？**登录同步**」。点击后打开设置窗口的数据同步页（`DataSyncConfig`）。这一步在创建任何提供商**之前**。
- 点击后，引导记下「等待同步」，并显示「正在等待同步完成……」。**等同步进入空闲状态**（模型和密钥都已经到达）后，用**严格判断**（3.4）检查一次：
  - 有可用来源 → 写 `completed`，销毁引导窗口，打开默认首页（首页设置也是同步过来的）。
  - 没有 → 说明具体原因，例如需要输入同步口令解开 Key，或这台电脑尚未安装对应智能体。同步回来的管家配置已齐全时，结束首次引导，转到相应设置页处理；管家配置尚未齐全时，留在引导里继续。
  - 之后每次同步进入空闲状态都再检查一次，直到用户离开这一页。
- 用户在引导里已经建了提供商、之后才想登录同步：走现有的冲突处理，本期不改。

## 5. 引导窗口

- 窗口标签 `onboarding`。`window.rs` 新增 `create_onboarding_window`：
  - 默认 1024×740，不可调整大小，居中。
  - 高度最多取工作区高度的 90%。在 768p 屏幕、125% 缩放下可用高度只有大约 614 逻辑像素，所以内容区要能滚动，页头和底部按钮固定。
- 标题栏沿用现有规则：macOS 用 Overlay（`with_macos_overlay_titlebar`），Windows 无边框加 `WindowControls`（`with_windows_custom_titlebar`），Linux 用原生标题栏。前端顶部用 `WindowTopBar`（参考 `ScheduleWindow`）。
- 接入改动：
  - `src-tauri/capabilities/migrated.json` 的 `windows` 加 `onboarding`。
  - `App.tsx` 的窗口标签映射加 `OnboardingWindow`。
  - 更新 `docs/architecture.md` 和 `docs/product/14-多窗口架构.md` 的窗口列表。
- 关闭事件：未完成时拦截并改为隐藏（4.3），完成时销毁。
- 完成后打开哪个窗口：
  - 躺平：调用 `open_butler_experiment_window`（窗口不存在时会创建）。
  - 专家：打开用户选择的首页。
  - 我自己填：二次确认后打开 `chat_ui`。
- 移动端不创建这个窗口，`mobile.json` 也不改。
- 视觉：黑白灰配色，用 shadcn 组件。顶部是步骤点（不写步骤名）；底部左侧是「我自己填」，右侧是主按钮；回车触发主按钮。

#### 7.1.1 本机智能体（P2，依赖第 11 节）

- **检测**：复用 `useLocalAgentDetection`（Codex、Claude Code 用 `check_acp_library`，其余用 `detect_native_agent_environment`）。只显示状态为 `installed` 的，顺序是 Claude Code、Codex、其余。ACP 下的每个已检测到的 CLI（例如 Gemini CLI）单独一张卡片。
- **Node 依赖**：原生驱动依赖 Node。`node.ok` 为 false 时，卡片显示「需要先安装 Node.js」并附链接，不可选。
- **选中后先建一个禁用的草稿提供商**，再用它的 id 去做检查。现有的账号检查接口都需要 provider id（`login_cursor`、`get_antigravity_login_status`、`get_provider_quota`），而只做安装检测时 provider id 是空的，拿不到账号信息。
- **默认参数**：Codex 优先读取本机参数，缺省审批策略为 `on-request`，沙箱为 `workspace-write`。ACP 把用户选中的 CLI 写入 `acp_cli_command`。Claude Code 沿用通道的权限模式，引导不写入额外的权限覆盖。
- **怎么确认能用**：

| 智能体 | 确认方式 |
|---|---|
| Cursor | `ToolStatus.account.signed_in`。未登录时卡片里出现「登录 Cursor」按钮，调用 `login_cursor`（浏览器登录） |
| Antigravity | `get_antigravity_login_status`。未登录时出现「登录」按钮，调用 `login_antigravity` |
| Codex | 用 `account/read` 检查账号要求，通过 `model/list` 读取列表 |
| Claude Code | 用 CLI 的 `auth status` 检查登录状态，读取初始化返回的型号 |
| ACP、Pi、OpenCode、Kiro | 通过所配置实例的原生通道读取型号，初始化失败或列表为空时提示原因 |

所有本机通道均须返回可用型号才可添加，检查过程不发送测试消息。

  - 填了可选 Key：从 API 模型列表选择并应用辅助角色，主模型仍然是智能体。未填时保留已有配置；首次配置按第 12 节处理缺失角色。

#### 7.1.2 有人发给我分享码

- 一个多行输入框。粘贴后自动解析（规则见第 13 节）：
  - 同时解析出分享码和密码：启用「下一步」，点击后导入并查看模型。
  - 只解析出分享码：输入框下方出现「密码」输入框。
- 检查步骤：
  1. 导入（`import_llm_provider`，改为返回新建行的 id，13.3）。导入的提供商记入 `onboarding_draft`，中途放弃时会被清理。
     - 解密失败：提示「密码不对」或「分享码不完整」。
     - 本机已经有同 api_type、同 endpoint、同 Key 的提供商：提示「你已经有这个配置了」，直接用已有的那个。
  2. 获取模型列表（`preview_model_list`）。
  3. 帮我选择（第 10 节）。
  4. 点「应用」保存所选角色使用的模型，同一提供商的相同模型保存一次。其余的用户以后可以在设置里添加。

#### 7.1.3 我有 {推荐服务商} 的 Key

推荐哪家服务商、用哪些模型、Key 怎么获取、价格提示，都由 helper 下发的引导预设决定（10.2）。应用内置一份兜底预设（DeepSeek）。下面以 DeepSeek 为例：

- 卡片标题里的服务商名称、「3 步获取」的内容，都来自预设。每一步都有直达链接，用系统浏览器打开。
- 检查步骤：
  1. 新建一个**禁用的草稿提供商**（`add_llm_provider`，api_type 和 endpoint 用预设里的值），写入 Key 和 `proxy_enabled`（按 `NewProviderWizard` 的规则）。
  2. 获取模型列表。认证失败就提示「Key 不对」。
  3. **只对 DeepSeek**：调用 `get_deepseek_balance`。作为主来源时，余额为 0 显示 [去充值]、[我已充值，重新检查] 和 [保存配置，稍后充值]。选择保存后保留提供商和 Key，写 `awaiting_recharge` 并允许关闭窗口；下次打开从余额检查继续。余额恢复后可选择模型并应用配置。仅作为可选的轻量或审核来源时，按 10.1 处理。
  4. 可用第 10 节的评分填写各角色的推荐型号。
  5. 点「应用」直接保存所选角色，同一型号可用于多个角色。
- 从 [代理设置] 改完代理回来重新检查时，先按最新的网络代理设置刷新草稿提供商的 `proxy_enabled`。
- **不把 Key 填进内置的禁用提供商。** 验证一律用草稿提供商。是否改为写入同类型、还没配置的内置提供商（避免出现两个 DeepSeek），在 7.2 写入时一次性决定。

#### 7.1.4 我用的是其他服务商

- P1 阶段，嵌入的目录里隐藏「本机智能体」这一组。
- 点「完成」保存连接并获取模型列表，回到来源页显示提供商名称与模型数量。点「下一步」查看列表，手动选择或在模型页点「帮我选」，确认后应用。
- 嵌入模式下，向导里最后一步「启用」改为由 7.2 统一执行。

### 7.2 一次写入全部配置

新增 Rust 命令 `apply_onboarding_config`，把下面这些写入**放在一个命令里完成**：可以重复执行，可以写单元测试，并且只做**部分更新**（`partial=true`）。

为什么不在前端逐个调 `save_feature_config`：它在 `partial=false` 时会先删掉整组配置（`system_api.rs::persist_feature_settings`）。逐个调用会把标题、总结、管家、飞书等已有设置一起清掉，也做不到第 4.5 节「只覆盖本次写入的键」的承诺。

| 顺序 | 写入内容 | 聊天主力选 API | 聊天主力选本机智能体（可另配辅助 API） |
|---|---|---|---|
| 1 | 提供商 | 草稿提供商写入模型并启用。如果有同 api_type、没有 Key 的内置提供商，就把 endpoint、Key、`proxy_enabled`、模型写进内置那条并启用，然后删掉草稿，避免出现两条同名提供商 | 启用智能体提供商 |
| 2 | 助手 1 的模型 | 主模型 | 不改（助手 1 不能改类型，也不能用智能体） |
| 3 | 新对话默认助手（本机） | 设为助手 1 | 设为所选智能体对应的 Agent 助手，同一次应用或重试复用同一助手 |
| 4 | `default_light_model` | 躺平写入从列表选定的轻量模型，专家写入通过检查的型号 | 同左 |
| 5 | 默认决策模型与工具审核设置 | 躺平将选定的审核模型写入 `default_decision_model`，工具审核沿用该模型。专家写入 `auto_review_model` 和 `auto_review_provider_id` | 同左，审核角色使用 API 模型 |
| 6 | 创建工作区目录（第 14 节） | ✓ | ✓（本机智能体运行时要求工作目录真实存在） |
| 7 | 管家配置：`butler_model_id`、`butler_main_workspace_path`（重跑模式下已有就不改）、`butler_main_workspace_description`（默认描述）、`butler_experiment_enabled=true` | 主模型 | 智能体 |
| 8 | `default_home_window=butler_experiment` | ✓ | ✓ |
| 9 | `onboarding_step=applied`、`onboarding_state=completed`、`onboarding_completed_at` | ✓ | ✓ |

- 表中第 6～8 步是躺平默认值。专家选「聊天」只把首页设为 `chat_ui`，跳过管家启用、模型绑定和工作区创建。选「管家」则使用 8.3 单独选定的管家模型和工作区。启用管家时，第 7、8 步在同一次 `experimental` 部分更新里提交，以便后端校验工作区。
- 两种模式共用模型分工（8.2）。聊天主力选智能体时，可单独添加 API 供轻量或审核使用；成功验证的辅助来源也保存并启用。未通过的角色按 10.1 保留原配置。
- **写完后**：
  - 启动后台准备任务（第 9 节）。
  - 如果预设里 `extras.enable_deepseek_search=true` 且来源是 DeepSeek，由前端调用 `deepseekSuite.ts::connectDeepSeekSearch` 顺便开启 DeepSeek 搜索（也就是 `NewProviderWizard` 里「一并启用」那段逻辑）。失败不阻塞，结果显示在「好了」页。其他来源保持现有的搜索默认设置。
- 两项都写好后，管家窗口不会再弹出总管家设置向导（它只在模型或主工作区缺失时才弹）。`butler_display_name` 不写，沿用默认的「总管家」。
- 任何一步失败：报错并停在当前页（躺平是第 1 页，专家是 8.4），`onboarding_step` 保持 `source_ready`。这些写入分布在几个数据库里，做不成一个事务，所以已经完成的步骤会保留；重试时从第 1 步重新执行一遍，因为每一步都可以安全地重复执行。

### 7.3 模型选择页

### 7.4 新对话默认助手

现在新建对话用的是助手列表里的第一个（`get_assistants` 没有排序，实际就是 id=1 的快速使用助手）。只有本机智能体的用户在聊天窗口新建对话时，会看到「没有配置模型」。

新增设备本地的 `default_new_chat_assistant_id`：

- 有值并且这个助手还存在时，新建对话默认选它；否则保持现状。
- 在助手管理页提供「设为新对话默认」。
- Ask 弹窗固定使用助手 1（`AskWindow.tsx`）。助手 1 缺少可用的 API 聊天模型时，Ask 显示「Ask 需要一个 API 模型，[配置]」，链接打开助手 1 的模型设置。即使其他 API 已用于轻量或审核，也按助手 1 的实际绑定判断。

## 8. 专家模式

### 8.1 提供商

- 嵌入完整的提供商目录（`NewProviderWizard` 嵌入模式），可以添加多个。上方列出已添加的提供商，可以删除。
- 目录上方有 [导入分享码]（和 7.1.2 一样是整段粘贴解析）。底部有「登录同步」。

### 8.2 模型分工

```

Ask 弹窗       快速使用助手 · DeepSeek / xxx
```

- 设计草图上这一页只有两个模型。审核模型默认跟随轻量模型并折叠起来，需要时展开单独指定。
- **新对话默认使用**：按「API 聊天模型」「本机智能体」分组，可任选已添加的来源。选 API 时绑定助手 1；选智能体时，使用对应的 Agent 助手作为新对话默认。躺平模式按来源自动填入，专家模式允许手动选择。
- **轻量和审核**独立于聊天主力。轻量模型可手动选择本机智能体返回的型号，选择后显示 token 消耗提醒。审核模型沿用 API 聊天模型；本机轻量模型不参与审核联动。

- 「帮我选」「全部帮我选」按第 10 节推荐并验证 API 模型。用户已选本机智能体作为主力时保留该选择，只推荐辅助 API。

## 9. 后台准备任务

### 9.1 任务内容

| 项 | 安装方式 | 已就绪判断 | 备注 |
|---|---|---|---|
| AIPP 官方 Skills | 从官方目录选择 aipp-skills，安装包中的全部技能 | 同一来源已经安装 | 安装后为快速使用助手启用扫描到的全部可用 Skills |

| bun | 和 `install_bun` 共用安装逻辑 | `check_bun_version` 不是 `Not Installed` | 装到应用数据目录的 `bun/bin`。下载源目前只有 npmmirror |
| uv | 和 `install_uv` 共用安装逻辑；引导安装时设置 `UV_NO_MODIFY_PATH=1` | `check_uv_version` | 官方脚本加 ghfast 镜像，最多重试 3 次。AIPP 自己会到 `~/.local/bin` 等目录找 uv，所以不需要改用户的 PATH，这样和 bun 一致：AIPP 管理的运行环境都不写入系统 PATH |

### 9.2 安装器要先改一下

现有命令不能直接拿来给后台任务用：

- `install_bun` 和 `install_uv` 只是起一个线程就立即返回，没有可以等待的结果，也不接受代理参数。
- uv 的 `uv-install-finished` 在 `emit_error` / `emit_success` 里会发，结束时还会再发一次，每次重试失败也会先发一个 `false`。
- 现在没有自动走代理重试的逻辑：`StepSkillsInstall` 是让用户手动点按钮重试；Office 插件只要配置了代理就走代理。

**改法**：把 Skills、Office、bun、uv 的安装各自抽成「可以等待结果、接受代理参数」的 Rust 函数。现有命令和后台任务都调用这些函数，并**共用同一把锁**，这样用户在设置页手动点安装和后台任务不会撞车。后台任务直接拿函数的返回值，不再通过事件去猜结果。

### 9.3 运行规则

- 新增 `onboarding/setup.rs` 任务管理器，在 `apply_onboarding_config` 写完后启动。它不依赖任何窗口，关掉引导窗口或管家窗口都会继续运行。
- **顺序**：Skills → Office 插件 → bun → uv，按「用户最快能感受到」排序，一项一项来，避免占满带宽。
- 每一项开始前先检查是否已就绪，已就绪就跳过。所以重复执行没有副作用。
- **代理**：配置了网络代理就走代理，否则直连（和 Office 插件现在的做法一致）。安装器内部已有的重试保留（例如 uv 的 3 次），任务本身失败后不再自动重试。
- **状态**：每一项的状态（`pending`、`running`、`done`、`skipped`、`failed` 加原因）写入 `onboarding_setup_status`。全局事件 `onboarding-setup-progress` 推送变化，命令 `get_onboarding_setup_status` 查询当前状态。
- **重启**：应用重启时，如果还有 `pending` 或 `running` 的项，自动继续执行一次（用户已经表达过要装）；`failed` 的项不自动重试。

### 9.4 进度入口

- 新增共用组件 `OnboardingSetupChip`，放在管家窗口和聊天窗口顶栏的右侧：
  - 进行中显示「正在准备 2/5」。
  - 全部完成后显示 3 秒「准备好了」，然后消失。
  - 有失败项时显示「N 项未完成」。全部任务结束后，可在详情底部点击「我知道了」收起提醒；重开窗口后仍保持收起。重新执行的任务再次失败时会重新提醒。
- 点击后弹出一个列表，显示每一项的状态和失败原因，失败项旁边有 [重试]。
- 引导完成页、聊天与管家窗口提供准备进度和重试入口。

### 10.3 匹配算法

只考虑实际可选的 API 模型。以当前服务地址和完整模型代码匹配该提供商的报价，以 canonical_model_id 关联底模评测。同一底模的多个别名或多个服务商报价只算一个评测来源。主力排除明确不支持工具的候选。

models.dev 提供底模身份、能力、专项评测和当前提供商价格。Helper 将 [Artificial Analysis](https://artificialanalysis.ai/) 的 Intelligence Index 和 [Arena](https://huggingface.co/datasets/lmarena-ai/leaderboard-dataset) 的对话、Agent 与事实性榜单快照合入目录。可在 Helper 运行 `python scripts/sync-onboarding-benchmarks.py --aipp <AIPP仓库目录>` 同时更新发布快照和离线目录。

能力以完整目录为参照，固定目录下模型分数与候选集合无关。同一专项的版本、条件、指标方向和推理档位共用一个参照组。AA 综合指数单独使用最新可校准版本，比较各模型在各自默认档位运行同一套任务的表现。模型默认档位未知时跳过明确标注档位的结果。每个底模在一项评测中只作一个参照。同分、置信区间相交或差距低于指标容差时各计半胜；加入两次中性观测减小小样本极端值的影响。仅有一个底模参加的项目不计分。

同领域的各项百分位先求平均，再按角色得到能力值 Q（0–1）。整个目录都缺少的领域不分配权重。模型有部分有效成绩时，其缺测领域取保守基线 0.35；该角色全无可用成绩时 Q 为 0。主力的综合指数、推理、任务执行、指令遵循和对话偏好权重依次为 60、12、20、5、3。轻量的综合指数、指令、上下文和事实性依次为 20、40、20、20。审核的误放行、安全、综合指数、推理、指令和事实性依次为 45、20、15、5、5、10。

推荐分 = w × Q² + (1 − w) / (1 + C / S)。C 为当前提供商每百万混合 tokens 的估算美元费用；主力、轻量、审核的输入占比分别为 80%、95%、90%。对应能力系数 w 为 0.90、0.40、0.80，价格分降到一半时的每百万 token 成本 S 分别为 2、0.35、1 美元。已知免费得到完整价格分，价格未知时价格分为零。综合分相同时先按成本，同一系列同价时优先较新发布日期，再按稳定标识排序。

### 10.4 专家模式的试调用

新增 Rust 命令 `probe_chat_model { providerId, modelCode }`：

- 用最小的请求：一条「hi」，`max_tokens=32`，超时 15 秒。
- 返回 `{ ok, kind, message, latency_ms }`。
- OpenAI 兼容提供商尚未保存模型协议时，先请求 Responses，仅在网关明确拒绝该接口时尝试 Chat Completions。两次请求共用 15 秒预算，使用同一模型与基址。成功后以提供商和模型保存协议。已保存协议、其他提供商的原生协议和目录推荐协议直接使用。
- 只要接口成功返回就算通过，**不管结束原因是什么、内容是不是空的**。会思考的模型，在 token 很少时可能只返回一部分思考内容，或者什么都不返回；如果把 `max_tokens` 设成 1，这类模型会直接报错。

`kind` 由新增的公共函数 `classify_provider_error` 根据状态码判断（使用 `genai::Error::status()`，现在这个值被丢掉了）：

| kind | 判断条件 |
|---|---|
| `auth` | 401、403 |
| `insufficient_balance` | 402，或者响应文字里提到余额不足 |
| `model_not_found` | 上游明确指出模型不存在 |
| `choose_protocol` | OpenAI 兼容网关返回原因不明的 404，或当前可试的协议均被拒绝，允许手动选择协议后重试 |
| `rate_limited` | 429 |
| `network` / `timeout` | 连接失败、超时 |
| `other` | 其他情况 |

`preview_model_list` 也改用这个分类，返回结构化的错误，前端按 7.6 的表显示文案。决策协议模型继续用现有的 `test_decision_model`。

## 11. 总管家使用本机智能体（P2）

### 11.1 现状

- 总管家系统助手的类型写死为普通助手：`butler_assistant_profile.rs::sync` 创建时写 `Some(0)`，之后同步也不会改。
- 走不走智能体，只看 `assistant_type == Some(4)`（`ai_api.rs`）。
- `get_butler_model_selection` 通过 `get_llm_model_detail` 读取模型，没有模型记录就报「无法读取总管家模型配置」。而本机智能体提供商没有模型记录。
- 管家模式里，**智能体类型的联系人和受托助手已经可以用**：`native_butler_role` 会把助手的角色说明传给原生驱动。所以这次要做的是让总管家本身也走这条已有的通道。

### 11.2 要改的地方

1. **`butler_model_id` 允许指向本机智能体**：格式仍然是 `{code}%%{providerId}`，code 用 `get_filtered_models_for_select(4)` 给出的合成编码（`__agent_default__` / `acp`），或者智能体自己的模型选项。`get_butler_model_selection` 遇到本机智能体提供商时，不再要求有模型记录。
2. **总管家的助手类型跟着大脑走**：`butler_assistant_profile::sync` 根据提供商写 `assistant_type`（智能体为 4，否则为 0），并按 Agent 助手的方式绑定提供商（模型 id 为 0 时存空编码，和 `add_assistant` 一致）。
3. **切换总管家的执行通道时重开主会话**：API 与本机智能体互换、从一个本机智能体换到另一个（如 Claude Code → Codex）都要先确认。同一驱动切到另一提供商实例也按切换通道处理，原生会话归属原实例。设置页、管家设置向导与首次引导结果页共用此规则。
   - 切换前确认：「切换总管家的大脑会开始一段新的主会话，之前的对话可以在历史里查看」。
   - 确认后调用 `reset_butler_main_conversation`。**不要用** `reset_butler_contact_conversation`，它会拒绝处理总管家。旧的主会话按 `butler_main_state` 区分，保留在历史里。
   - 取消时保留原配置和主会话。API 换 API 可继续当前主会话；同一智能体实例内仅切换模型时沿用该驱动已有的会话规则。
4. **工作目录**：总管家走智能体时，以主工作区作为工作目录。目录必须存在，引导会负责创建（第 14 节）。
5. **工具**：在会话类型是 `butler_main`、助手是 Agent 类型时，确认以下工具都能通过原生驱动的 scoped MCP 拿到：
   - 总管家专用工具（派发和操作独立任务，见 `templates.rs::is_butler_main_only_agent_tool`）；
   - SuperAdmin、`schedule_task`、`report_progress`、`preview_message`。
   联系人用的是同一套注入方式，但**实现时仍要逐项验证**。
6. **会话命令**：`/compact` 走原生压缩（Agent 已支持）；`/reload` 需要能更新 `native_butler_role`，要验证。
7. **主动整理的深度整理**：现在只有 `deep_model` 显式写成 `assistant:<id>` 时才走原生智能体（`proactive/agent.rs`）。留空时会读总管家模型，按 HTTP 方式调用。要改为：总管家是智能体且 `deep_model` 为空时，视为 `assistant:<总管家助手 id>`。
8. **其他读取总管家模型的地方**：`host_bridge/chat.rs`、`deepseek_api.rs`、群聊调度和主动整理的回退链，都会读 `butler_model_id`。遇到本机智能体时，要逐个改为跳过或者走智能体，不能按 HTTP 发请求。
9. **飞书投递和定时任务**：总管家是智能体时，飞书消息和定时任务的执行、投递都要验证。定时任务无人值守时的审核规则不变。
10. **选择器**：
    - 总管家模型的下拉框**包含**本机智能体，按「API 模型 / 本机智能体」分组。涉及 `ButlerConfigCenter`、总管家设置向导、引导 8.3。
    - 小型辅助模型、群聊调度模型的下拉框**排除**本机智能体。

### 11.3 验收

## 14. 运行环境与工作区

### 14.1 工作区

- 默认路径 `~/AIPP`：Windows 上是 `%USERPROFILE%\AIPP`，macOS 和 Linux 上是 `$HOME/AIPP`。用 `create_dir_all` 创建，已经存在就直接使用。
- **为什么不放在 `~/.aipp` 或 AppData**：主工作区是管家存放产出文件的地方，用户需要找得到，这两个位置默认是隐藏的。
- **为什么不放在「文档」**：Windows 上「文档」经常被 OneDrive 接管。AI 一次产生大量小文件（比如 `node_modules`）时，OneDrive 会一直在同步。
- **为什么用英文名**：一些 CLI 工具和 Python 脚本处理中文或带空格的路径有问题。用户名本身是中文的情况没法避免，本期不处理。
- 「好了」页有 [打开文件夹]。
- 工作区描述用默认文案 `BUTLER_MAIN_WORKSPACE_DEFAULT_DESCRIPTION`。

### 14.2 bun 和 uv

- **bun**：组件预览（React / Vue）只认 bun（`BunUtils::detect` 只找 `bun`），装了 Node 也替代不了。bun 装在应用数据目录，不需要管理员权限。
- **uv**：Python 部分会先找系统里的 Python 3（`python_utils.rs`），但安装依赖、隔离环境都靠 uv。另外，Windows 上 PATH 里的 `python` 经常是微软商店的占位程序，不可靠。uv 用官方脚本装在用户目录，不需要管理员权限。引导安装时不修改 PATH（9.1）。
- **结论**：两者都按「检测到能用就跳过，没有就在后台静默安装」处理，不影响用户已有的 Node 和 Python。

## 17. 风险与已知问题（本期不修）

- **工作区路径会跨设备同步**：`feature_config` 里除了 `data_sync` 和 `butler_proactive`，其他全部同步，包括主工作区路径（每台电脑不一样）和 `default_home_window`。第二台设备同步后会拿到第一台的路径。这是现有问题，需要单独处理。
- **没有单实例保护**：引导进行中再次启动应用，会起第二个进程。
- **`is_claude_code_provider("anthropic")` 返回 true**：`validate_binding` 可能因此拒绝把普通助手绑定到 Anthropic API，需要单独确认。本次新增的判断函数不复用它。
- **bun 只有 npmmirror 一个下载源**，没有备用。海外网络可能下载失败，失败后可以重试。
- **Claude Code、ACP、Pi、OpenCode、Kiro 没有登录状态接口**，登录问题要到第一次对话时才会暴露（7.1.1）。
- **用户名是中文时**，`~/AIPP` 的完整路径里仍然有中文。

## 18. 实施顺序

**P1：引导主体**（不依赖 P2 也能完整使用）

## 19. 已确认的决定

1. 入口是两张带插画的卡片，叫**躺平**和**专家**（不用「折腾」，那样显得选的人很执拗）。插画使用现有的动画头像加配件，效果看过之后再定。
2. 躺平模式不让用户挑模型：选卡片 → 粘贴一样东西 → 开始使用。安装全部放到后台，不挡路。
3. 躺平模式完成后开启管家，默认首页改为管家。
4. 本机智能体可担任主模型、总管家和轻量模型。添加前读取实例模型目录并验证连接。手动选择具体型号作轻量模型时提示额外 token 消耗，工具审核仍使用单独的 API。
5. 帮我选择使用同一份目录，按每个角色的评测和当前报价排序，并验证可用性。
6. 工作区默认 `~/AIPP`。bun 和 uv 检测到能用就跳过，否则在后台静默安装。飞书以后再接。
7. 「导入」指的是 AIPP 自己的分享码。导出时生成可以整段转发的消息，导入时粘贴整段即可。
8. 管家模型和主工作区已设置时关闭首次引导的所有入口；管家尚未配齐时，跳过后仍可手动继续。触发与恢复见第 4 节。
9. 本期只做桌面端。一键搬家以后再做。
10. 按第 18 节划分 P1 / P2，用来描述依赖关系和验收范围；实际开发基本一起推进。
11. 审核单独评分；手动关联时使用轻量模型。
12. 分享消息默认包含密码，分享方可以取消勾选，对话框里有费用提醒。
13. 引导安装 uv 时不修改 PATH，和 bun 一致；用户在自己的终端里用不了 `uv` 命令，可以接受。
14. DeepSeek 主来源余额为 0 时可以保存配置，稍后充值并从余额检查继续。
15. 主来源通过检查即可完成；轻量、审核模型失败时分别提示影响并允许重试。
16. 两种模式共用模型分工，均支持智能体聊天、API 做轻量和审核；Ask 沿用助手 1。
17. 总管家更换原生通道（如 Claude Code → Codex）须先确认，确认后重开主会话，历史保留。
