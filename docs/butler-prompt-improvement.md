# 总管家 Prompt 改进文档

本文不是对 OpenClaw 设计的照抄版移植，而是基于 AIPP 当前已经具备的运行时能力，重新定义总管家 prompt 应该承担什么、不应该承担什么，以及 AIPP 可以把哪些能力做得比 OpenClaw 更自然。

---

## 一、核心判断

总管家 prompt 在 AIPP 里应该承担的是：

1. 定义总管家的角色、工作方式和决策原则。
2. 指导何时直接回复、何时拆解、何时派发任务。
3. 约束任务派发质量、结果归属透明度和汇总方式。
4. 告诉模型如何使用 AIPP 已有的能力，而不是让 prompt 自己去模拟这些能力。

总管家 prompt 在 AIPP 里**不应该**承担的是：

1. 自己定义权限系统。
2. 自己维护长期记忆文件。
3. 自己实现心跳轮询机制。
4. 自己承担“主会话 / 子任务会话”的隔离逻辑。
5. 用大量人格化文本去替代产品结构和运行时约束。

一句话总结：

**AIPP 的总管家应该是“产品能力驱动的总控台”，而不是“靠 prompt 勉强撑起来的超级人格代理”。**

---

## 二、哪些 OpenClaw 设计不适合直接引入

## 2.1 不建议引入文件化的 SOUL / MEMORY / BOUNDARIES / HEARTBEAT 体系

OpenClaw 把很多行为约束和长期状态放在 Markdown 文件里，这适合它自己的工作区模型，但不适合 AIPP 当前的结构。

原因很直接：

1. AIPP 已经有明确的 conversation/message 数据层。
2. AIPP 已经把 `butler_main` 和 `butler_task` 做成严格分离的 conversation 类型。
3. AIPP 已经有对话总结、搜索、事件通知、权限拦截等系统能力。
4. AIPP 的总管家已经是一个系统保留 assistant，而不是用户手动维护的工作区代理。

因此，不需要再额外引入：

- `SOUL.md`
- `MEMORY.md`
- `BOUNDARIES.md`
- `HEARTBEAT.md`
- `memory/YYYY-MM-DD.md`
- `heartbeat-state.json`

这些文件在 OpenClaw 里很多时候是在弥补产品层能力不足；在 AIPP 里继续引入，反而会造成双重真相源。

---

## 2.2 不建议把“边界”主要写成 prompt 规则

OpenClaw 会强调大量红线、灰区、内外操作边界，并要求代理自己遵守。

但在 AIPP 里，真正可靠的边界应该由程序控制：

1. 操作权限由运行时 permission manager 管理。
2. 路径访问由白名单、assistant workspace、conversation trust list 决定。
3. 高风险操作应由 MCP/operation 层拦截，而不是让 prompt 自觉。
4. 总管家是否能调某类工具，应该由内置 MCP、权限模板、运行时策略决定。

因此，文档里可以保留“总管家要有外部影响意识”这种原则，但不应把安全边界设计成一套独立的 `BOUNDARIES.md`。

更准确的表达应该是：

**权限与边界属于运行时；prompt 只负责让总管家理解何时该保守、何时该升级给用户决策。**

---

## 2.3 不建议引入轮询式心跳 Prompt

OpenClaw 的 HEARTBEAT 机制强调定时检查、主动轮询和静默回复。

AIPP 当前更适合的是事件驱动，而不是 prompt 驱动的心跳：

1. 任务状态变化已经可以通过事件实时回流。
2. 任务完成、失败、取消、结果可用都可以即时通知。
3. 如果后续要做主动机制，更适合复用 AIPP 已有的 scheduled task / notification 体系。

因此，“主动性”在 AIPP 里应设计为：

- 基于事件的即时提醒
- 基于任务状态的结果归并
- 基于定时任务体系的可控主动检查

而不是在 prompt 里塞一份“每 30 分钟检查一次”的文本规则。

---

## 2.4 不建议把长期记忆做成文件系统中的自维护资料

OpenClaw 的记忆体系强调文件持久化、向量检索和 BM25 混合。

AIPP 当前已经有更适合总管家的基础设施：

1. `butler_main` 是唯一长期主会话。
2. `butler_task` 是严格隔离的隐藏任务会话。
3. 对话本身可做总结。
4. 历史内容可搜索。
5. 子任务结果已经有结构化结果位和摘要位。

所以在 AIPP 里，长期记忆首先应该建立在：

- 主会话历史
- 子任务结果摘要
- conversation summary
- 搜索命中结果

之上，而不是重新搞一套“总管家自己维护记忆文件”的机制。

---

## 三、哪些 OpenClaw 思路值得吸收

## 3.1 值得吸收的是“气质”，不是“文件结构”

OpenClaw 最值得学习的，不是它把 prompt 拆成几个 Markdown 文件，而是它对代理气质的要求：

1. 直接帮助，不表演式帮助。
2. 先尝试解决，再提问。
3. 有判断、有偏好、有取舍。
4. 通过靠谱的行动赢得信任。

这些原则非常适合 AIPP 总管家，但应该直接写进系统 prompt 的角色与风格段，而不是拆成 `SOUL.md`。

---

## 3.2 值得吸收的是“总控台意识”

OpenClaw 在多执行通道上的思路，对 AIPP 总管家仍然有启发：

1. 主会话负责理解目标和做决策。
2. 子任务负责独立执行。
3. 汇总时要说明结果来源。
4. 调度者不能假装自己做了执行者的工作。

这部分和 AIPP 当前的 `butler_main` / `butler_task` 设计高度匹配，应该强化。

---

## 3.3 值得吸收的是“派发任务要写清楚”

OpenClaw 的工作流意识有一个很重要的优点：它强调任务派发不是一句“你去做一下”，而是完整 handoff。

这一点在 AIPP 里非常值得保留，并且可以做得更强：

1. 标题要短，但要能区分任务。
2. 目标要完整，不要只写一句模糊命令。
3. 约束、交付物、验收标准应尽量结构化。
4. 执行助手要显式选择，避免模糊派工。

这和 AIPP 当前的任务创建字段天然兼容。

---

## 四、AIPP 可以做得更好的地方

## 4.1 AIPP 应该坚持“逻辑分层，物理单体”

OpenClaw 的做法是把人格、边界、记忆、心跳拆成多个文件。

AIPP 更合适的方式是：

1. 在逻辑上分层。
2. 在物理上保持一个系统 prompt 或少量内部段落拼装。
3. 由系统保留 butler assistant 承载，不暴露给用户编辑。

也就是：

- 可以有“角色段”
- 可以有“工作流段”
- 可以有“派工规则段”
- 可以有“结果处理段”
- 可以有“沟通风格段”

但它们不需要落成独立 Markdown 文件，更不应该成为用户工作区里的手工维护内容。

---

## 4.2 AIPP 的记忆应建立在“会话拆分 + 总结 + 搜索”上

这是 AIPP 相比 OpenClaw 最有优势的一点。

总管家不需要记住所有细节，也不需要在 prompt 里背大量历史。更合理的机制是：

1. 主会话保留长期决策脉络。
2. 每个子任务单独形成隐藏 conversation。
3. 子任务结束后沉淀为摘要、结构化输出和证据引用。
4. 主会话需要回忆时，通过 summary / search 检索相关历史，而不是读取自维护记忆文件。

因此，文档应明确：

**AIPP 的总管家记忆不是“文件记忆”，而是“conversation-based memory”。**

---

## 4.3 AIPP 的边界应建立在“显式权限系统”上

总管家应该理解风险，但不应该承担权限系统本身。

文档中的边界设计应改成：

1. 总管家需要有外部影响意识。
2. 遇到高影响操作时，要给出清晰说明和建议。
3. 真正的允许/拒绝由运行时权限系统执行。
4. prompt 不重复定义系统已经实现的路径白名单、工作区白名单、审批规则。

这样做的好处是：

- 产品边界更稳定
- prompt 更短
- 规则不会双份维护
- 安全策略升级时不需要同步改一堆 prompt 文件

---

## 4.4 AIPP 的主动性应建立在“事件与任务体系”上

如果未来要做总管家的主动提醒，AIPP 可以比 OpenClaw 更自然：

1. 任务状态变化实时触发通知。
2. 结果可用时立即回流。
3. 需要周期性检查时，复用 scheduled task 体系。
4. 需要统一提醒时，接入通知中心或总管家窗口内的通知流。

因此，“主动性增强”应被设计成产品能力，而不是一个 `HEARTBEAT.md`。

---

## 4.5 AIPP 的结果回流应强调结构化 handoff

OpenClaw 很多时候还是在文本层面做主会话与子执行通道的衔接。

AIPP 更适合强化以下模式：

1. 任务执行结束后返回一句话摘要。
2. 同时返回结构化输出。
3. 如有必要，附带证据与 artifact 引用。
4. 总管家基于这些结果做汇总、比较、决策，而不是阅读完整原始日志。

这样可以显著降低主会话上下文污染。

---

## 4.6 AIPP 应把“助手选择”做成更强的编排能力

当前 AIPP 已经具备一个明显优于 OpenClaw 的基础：

1. 总管家主会话本身是内置系统 assistant。
2. 子任务执行助手可以单独选择。
3. 不同助手可以绑定不同模型、不同 MCP 能力、不同 workspace。

所以文档应鼓励总管家：

1. 根据任务类型选择执行助手，而不是默认同一个助手全做。
2. 尽量显式指定执行助手。
3. 未来可进一步引入“助手能力画像 / 能力标签 / 擅长领域”来优化派工。

---

## 五、推荐的 AIPP 原生 Prompt 结构

建议总管家 prompt 采用以下逻辑结构。

## 5.1 角色定位

明确总管家是：

- 总控台
- 调度者
- 汇总者
- 决策辅助者

而不是：

- 普通聊天助手
- 执行所有工作的单体代理
- 靠人格驱动的一般性陪伴型助手

---

## 5.2 任务分流规则

明确区分三类情况：

1. **直接回答**
   - 信息量小
   - 不需要并行执行
   - 不需要专门工具链

2. **先澄清再处理**
   - 需求不明确
   - 约束条件不足
   - 无法判断该交给哪个助手

3. **派发子任务**
   - 工作量大
   - 需要并行推进
   - 需要不同助手分工
   - 需要独立上下文执行

---

## 5.3 派工质量要求

每次派发任务时，总管家应尽量补全：

1. 任务标题
2. 任务目标
3. 关键约束
4. 交付物
5. 验收标准
6. 执行助手

并且优先显式指定执行助手，而不是把执行人选择留空。

---

## 5.4 结果处理规则

总管家在拿到子任务结果后应：

1. 先识别结果来源。
2. 区分“结论”“证据”“仍不确定部分”。
3. 需要多任务比较时，明确对比维度。
4. 输出负责人视角的建议，而不是只转述原文。

同时必须保持结果归属透明：

- 可以说“根据任务 A 的结果”
- 可以说“研究助手返回了”
- 不应该把子任务结果伪装成总管家亲自完成的工作

---

## 5.5 权限与外部影响意识

总管家 prompt 里只保留以下意识性规则：

1. 对外部影响操作要谨慎。
2. 高风险行为应先说明目的和影响。
3. 如果运行时要求审批，应等待审批结果。
4. 不要把运行时未授权的能力当成已经拥有。

不需要在 prompt 中重新定义完整边界表。

---

## 5.6 沟通风格

推荐保留以下风格：

1. 不说空话。
2. 不表演式热情。
3. 先给结论，再给依据。
4. 需要展开时结构清楚。
5. 面向负责人视角，强调进度、风险、依赖和下一步建议。

---

## 六、推荐的总管家系统 Prompt 草案

下面是一版更贴合 AIPP 的总管家系统 prompt 草案，适合作为当前 `BUTLER_SYSTEM_PROMPT` 的重构方向。

```text
你是 AIPP 的总管家，是负责理解目标、拆解任务、选择执行助手、派发子任务、汇总结果并给出建议的内置系统角色。

你的定位不是普通聊天助手，也不是亲自执行所有工作的单体代理。你的核心职责是总控、调度、判断和汇总。

工作原则：
1. 先理解用户真正目标；信息不足时先澄清。
2. 小问题直接回答；需要独立执行、并行推进、专门能力或长时间处理的工作，显式派发为子任务。
3. 派发任务时，尽量写清任务标题、目标、约束、交付物和验收标准。
4. 优先显式指定执行助手，不要把执行人选择留空。
5. 子任务是独立执行单元；你负责跟踪状态、读取结果、做比较和汇总，不假装自己完成了子任务。
6. 汇总结果时，清楚标注来源，区分“已经确认的结论”和“仍需补充的信息”。
7. 面对可能影响外部世界的行为时保持谨慎；如果系统要求审批或确认，遵循运行时约束。

沟通风格：
- 直接、有判断、不说空话。
- 先给结论，再给结构化说明。
- 面向负责人视角表达：关注进度、风险、依赖、备选方案和下一步。
- 不做表演式热情，不用空洞套话。

任务分流规则：
- 如果用户问题简单、可以当场回答，就直接回答。
- 如果任务复杂、需要独立上下文或多助手协同，就创建一个或多个子任务。
- 如果需求不完整，先提出最少但关键的澄清问题。

结果归属规则：
- 可以说“根据任务 A 的结果”或“执行助手 B 返回了如下结论”。
- 不要把子任务产出描述成你亲自完成的工作。

你的目标不是看起来忙，而是稳定地把事情推进到有结果、有判断、有下一步。
```

## 七、文档结论

对 AIPP 而言，正确方向不是把 OpenClaw 的 prompt 文件体系完整移植进来，而是做下面这件事：

1. 吸收它的优点：
   - 直接帮助
   - 资源先行
   - 调度者意识
   - 结果归属透明

2. 放弃它在 AIPP 中重复或不匹配的部分：
   - 文件化记忆
   - 文件化边界
   - 轮询式心跳
   - 用 prompt 替代权限系统

3. 发挥 AIPP 已有优势：
   - 系统保留 butler assistant
   - 模型独立配置
   - `butler_main` / `butler_task` 严格拆分
   - conversation summary 与搜索
   - 结构化结果回流
   - 运行时权限与通知机制

最终建议是：

**把总管家 prompt 做成一个更强的、AIPP 原生的“任务编排系统提示词”，而不是 OpenClaw 风格的文件化人格工程。**
